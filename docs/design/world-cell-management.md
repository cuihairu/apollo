# world 与 cell 管理设计

> 状态：评审草案。本文细化已经确定的管理/执行边界，不代表独立 cell、远程调度或连续迁移已经实现。先评审方案，再调整实施清单和代码。

## 1. 结论与范围

方案可行，建议采用：**world 管理空间分配，cell 执行模拟，Base 持有长期资料**。默认一台主机运行一个 World 管理进程，自动维护一个或多个独立 cell 进程；管理和执行共用 `world` 二进制，用启动角色区分，仍走同一套注册、命令和权威校验。

本文中的“CellApp”只用于对照 BigWorld，Apollo 的执行角色仍叫 `cell`。共享二进制不会增加 `cellapp` 角色别名，也不把 Cell 分区改叫进程。大写 `Cell` 是分区；Space 对应现有 Scene 的空间语义；Instance 保留八态玩法生命周期。

第一阶段支持多个执行进程，**每个 Space 只有一个完整 Cell**。扩容按需启动 cell，再把新 Space 分配到就绪执行进程；缩容先自然排空，已有 Space 暂不因负载变化自动搬迁。后续补完整 Space/Instance 的连续迁移，最后按需求实现同 Space 多 Cell、Ghost 和无缝边界。

### 1.1. 应用目录与二进制

本草案采用本轮讨论的短名：目录、CMake 可执行目标和最终程序名统一，不带 `Server`、`-server` 或 `-app` 后缀。命名迁移已完成，没有保留另一套可用别名；world 缺省即管理角色，`--role=cell` 选执行角色。

| 应用目录 / 程序 | 职责 |
|---|---|
| apps/gateway / gateway | 客户端连接、会话与转发 |
| apps/login / login | 认证、服务目录与位置投影 |
| apps/base / base | 长期玩家对象与基础业务 |
| apps/world / world | 默认管理角色；`--role=cell` 执行角色 |
| apps/database / database | 存储访问与持久结果 |
| apps/machined / machined | 本机进程监督 |

cell 的装配与实现放在 World 应用或共享库内，保留模块边界，不建立另一个应用二进制。曾存在的宿主演示入口（apps/game-server）已移除，其宿主职责由 world 与共享库承载，不作为短名方案之外的部署角色。运维工具如 logger、admin、fleetctl 按自身职责保留，不因本案统一改名。

C++ 类型名不随可执行文件机械改写：Base 部分为 `base::Avatar`，Cell 部分为 `cell::Avatar`。

## 2. 所有权与调用路径

| 角色 | 唯一负责的状态 | 正常调用路径 |
|---|---|---|
| world | cell 注册、Space/Cell 分配、容量预留、拓扑版本、创建/迁移决定和排空 | 接收 Base 的空间申请，向 cell 发控制命令，发布已提交位置 |
| cell | 本地 Cell 的 Entity/Avatar、AOI、战斗、Lua、模拟时钟；当前活动的 Instance | 接收 gateway 模拟输入，向 gateway 下发模拟结果，向原 Base 提交业务请求 |
| base | `base::Avatar`、玩家长期资料与业务规则、结算去重 | gateway 基础业务 → Base → database；cell 结算 → 原 Base → database |
| login | 认证、服务地址和玩家位置投影 | 注册、查址、更新投影；不决定 Cell 分配 |
| gateway | 客户端连接、会话与 Base/cell 路由缓存 | 模拟输入直达 cell，不逐帧经过 World 管理端 |
| 本机监督机制 / machined | 本机进程启停、存活检测与重启退避 | 默认 World 复用监督代码管理 cell 子进程；独立 machined 模式下由它执行本机启停，不授予模拟写权 |

world 不持有第二份 Avatar，也不推进 Scene tick。cell 不持有完整玩家档案，不连接各小服数据库，不通过远程伪装成本地 Anchor 指针调用。Instance 的共享目标、计时和结算由一个明确的执行方负责；首阶段就是承载整个 Space 的 cell，World 只记其位置和生命周期投影。

默认“每台一 World”是单机部署约束，不把主机地址写成 World 的逻辑身份；也不要求将来一个 World 永远只能管理本机 cell。一个 cell 属于一个 world 管理范围。多 world 按配置管理互不重叠的范围；同一个逻辑 World 同时只允许一个活动管理进程。共享跨服执行池也有明确的所属 World，不能让两个 World 同时分配同一个执行进程的容量。

## 3. 身份、版本与最小记录

以下是语义字段，不是已经加入 wire 的字段；消息编号和字段演进必须经过现有契约生成链。

| 记录 | 必须表达 | 约束 |
|---|---|---|
| 执行进程 | cell 逻辑 ID、进程启动代次、所属 World、控制/模拟地址、版本与能力、就绪/排空状态 | PID/IP 不能当稳定身份；重启获得新代次，旧连接不能覆盖新注册 |
| Space | 稳定 Space ID、地图资源引用、所属 World、可选 Instance、生命周期 | Space 身份不依赖承载进程；实例 ID 与地图 ID 均不能替代 Space ID |
| Cell 分配 | Space ID、Cell ID、分区范围、承载进程及代次、拓扑版本、分配状态 | 默认范围覆盖整个 Space；将来可表达邻接和多个分区 |
| 实体位置 | 稳定实体 ID、Space/Cell、承载进程、模拟权威代次、会话/路由版本 | Base 归属版本独立；玩家跨服后仍指向原 Base |
| 创建/迁移操作 | 稳定请求 ID、来源和目标、预期版本、阶段、快照摘要、提交决定、清理进度 | 重试查询同一操作；不因超时换 ID 创建第二份活动 |

Space/实体/操作 ID 在互通范围内必须唯一，不能只用各进程从零递增的整数。若现有玩家 ID 仅区服内唯一，跨服键必须包含原区服，或先完成全局 ID 规则；不默认当前 ID 已满足要求。

分配以 World 为准，执行以 cell 的有效授权为准，目录与 gateway 只缓存已提交结果。进程启动代次、World 管理代次、模拟权威代次、拓扑版本、Base 写权和会话版本各有用途，不能用一个 `route_version` 统代。

## 4. 启动、注册与失联

1. World 取得该逻辑 World 的独占运行资格，恢复管理记录，进入恢复状态；恢复完成前不分配新空间。
2. cell 从配置或服务目录解析所属 World 地址，以经过认证的服务身份注册，声明启动代次、协议/快照能力和容量。没有同机 machined 也能独立注册。
3. World 验证所属关系、版本和身份，返回管理代次及注册结果。cell 完成依赖、地图/脚本加载能力和模拟入口检查后报告就绪；进程存活不等于可分配。
4. World 只向就绪且未排空的 cell 下发分配。cell 心跳报告活跃分配、tick 延迟、队列、内存与预留占用；旧代次心跳和迟到回执被拒绝。
5. cell 断开后，World 停止向它分配新工作并标记存疑，先查询和对账，不能立即在另一端重建同一份权威模拟。

**首阶段故障策略：优先保持单写者，不自动故障接管。** 心跳超时只证明不可达，不证明进程已死。控制链路失联时，cell 在配置的有限宽限期内继续已有活动；宽限期到期后在 tick 边界冻结模拟并停止新的外部业务副作用。IO 层同时关闭新输入受理。恢复连接后也必须先核对分配和管理代次，不能自行解冻。

宽限期使用本地单调时钟；部署前按心跳周期、网络抖动和允许停顿实测配置。**租约到期或代次递增本身不是旧端已被隔离的证明**：旧端可能暂停后恢复，Base/gateway 也可能持有旧缓存。重新授权目标前必须取得源冻结确认，或通过可验证的进程终止/访问隔离排除旧端；无法确认时保持阻塞。未来自动接管需要另外设计仲裁、授权期限和所有副作用接收端的隔离验证。

### 4.1. 共用二进制，分角色启动

建议目标启动形式如下；**这是待实现的 CLI，不是当前可执行命令**：

```text
world
world --config=<world-config>
world --role=cell --config=<cell-config>
```

World 角色启动管理循环和本机监督，不创建模拟宿主；cell 角色启动模拟宿主和注册客户端，不再拉起子 cell。不带参数或未指定 `--role` 时默认 World，使用默认配置来源；显式 `--role=world` 也表示同一管理角色，不是另一种模式。`--role` 缺少值、角色未知或配置非法时明确报错，不根据端口猜测角色。角色在启动时固定，不做运行中切换。

World 自动生成子进程的角色、逻辑 ID、所属 World 地址、独立运行目录和启动凭据，开发者无需为每个 cell 手写一份配置。启动凭据不放进可公开日志；端口可由执行端绑定后通过认证注册回报，不依赖先探测空闲端口再启动的竞态流程。

共享 main 只负责参数校验和角色装配，管理逻辑、模拟逻辑、监督机制保持模块边界；日志、指标、崩溃报告使用实际角色、逻辑 ID 和启动代次，不能因为文件名相同都标为 World。cell 不打开 World 管理日志或 Base 资料目录。

默认由 World 决定期望 cell 数并调用本机监督机制执行启停；复用现有 `apps/machined` 的监督思路，提取可复用实现，补动态增删与角色启动。现有监督实现以 POSIX 和固定 roster 为主，不能视作跨平台自动伸缩已完成；启动参数用结构化 argv，POSIX 优先采用适合多线程宿主的 spawn/exec 封装，Windows 单独实现进程句柄与回收。

已有 machined 部署中，可改为 World 提交期望启停、machined 执行；**同一子进程不能同时被两处重启监督**。World 本身由系统服务、容器或 machined 监督。跨主机启停需要目标主机监督端或外部编排，不能把本地 spawn 当远程启动。

### 4.2. 自动扩容和自然缩容

| 决策 | 规则 |
|---|---|
| 最小/最大进程数 | 默认最少一个 cell；最大值按 CPU、内存和宿主保留预算设置，不能无限派生 |
| 扩容 | 持续容量不足或达到高水位时，在冷却期和最大值内启动新 cell；启动中计入期望数量，防止重复拉起 |
| 就绪 | 子进程创建成功只代表启动中；认证注册、能力检查和就绪成功后才分配 Space；超时启动清理并有限退避 |
| 缩容 | 持续低水位且超过最小数量时，选择可排空的 cell 停止新分配；没有活跃/准备中 Space、在途迁移和未确认结算后才退出 |
| 取消缩容 | 尚未发出退出命令且重新缺容量时可取消排空；已经退出中的进程不能重新分配 |
| 无法排空 | 长驻 Space 或未结束活动使 cell 保持运行；期限到期报告阻塞，不以自动缩容名义强杀活动 |
| 故障重启 | 区分正常缩容退出与异常退出，重启次数有上限；新进程新代次，不自动冒认旧活动已恢复 |

扩容依据汇总容量、tick 延迟和队列的持续窗口，扩/缩阈值分离并设置冷却，避免抖动。增加 cell 只能分摊可独立分配的 Space；同一热点 Space 仍只有一个 Cell，增加进程不会自动加速它。单机资源已满则拒绝新活动或由部署层加主机，不继续堆进程。

管理日志记录子进程逻辑身份、启动代次、启动中/排空/退出意图和监督归属。World 重启先核对遗留 cell，再补足数量；不能看到子进程不在新管理进程的子列表就再拉一套。PID 可能复用，须结合启动身份和经过认证的重注册；无法确认归属时先隔离对账。

二进制发布使用版本目录或等效的不可变发布产物；World 拉起指定版本的同一程序，记录构建和协议能力。更新不覆盖正在运行的文件，不因路径同名误拉起旧版本。升级期间允许旧/新 cell 运行不同版本的同名二进制；旧 World 是否能启动新 cell 取决于已实现的控制协议兼容性。

## 5. Space 创建、容量与销毁

| 阶段 | 行为及确认 |
|---|---|
| 申请 | Base 校验队伍、资格、版本和玩法规则，提交稳定请求 ID；World 不重复实现业务资格规则 |
| 预留 | World 过滤就绪/兼容/准入范围，按配置预算与负载选择 cell，记录容量预留和创建意图；没有容量明确拒绝 |
| 准备 | cell 幂等创建完整 Cell 与本地 Scene，加载资源并按需要创建 Instance；此时不接收玩家输入、不推进活动 |
| 提交 | World 持久记录分配决定，发激活命令；cell 完成激活后确认，World 再发布可用路由和入场凭据 |
| 入场 | 玩家绑定原 Base、只读玩法快照、会话和有期限准入；cell 校验后创建唯一权威 Avatar |
| 销毁 | cell 停止准入，完成玩法结束与必要结算确认，释放模拟资源；World 记终态并回收容量 |

创建超时先查同一操作，准备资源只有在确认未提交后才允许取消回收。回执丢失不重新创建；提交后激活失败走恢复或显式失败清理。销毁请求必须校验分配代次，迟到请求不能删除新分配。

容量不只看在线人数：至少统计 tick 耗时、实体数、内存、输入积压和已预留资源。World 保存预留账，避免多个并发创建都看到同一份空闲容量；cell 再执行本地硬上限校验。满载先拒绝新活动，保留现有活动预算，不立即触发自动迁移。单进程多 Space 首先沿用一个模拟线程顺序 tick，接受其故障与卡顿影响范围；并行化以后再按写入边界实施。

结算未持久确认时必须保留可恢复记录；可以卸载大块地图资源，但不能删除唯一结算凭据。cell 崩溃后的补偿不是 World 根据内存投影猜测发奖，见[跨服设计](./cross-server-scenes.md)。

## 6. 管理记录与 World 重启

World 必须保存：Space/Cell 分配和版本、创建/迁移请求与提交决定、容量预留、Instance 负责人及结算恢复记录的位置、排空状态。心跳负载和地址缓存可以重建；“已提交还是未提交”不能只放内存或普通日志。

建议首阶段使用 **World 自己的持久管理日志与检查点**，不把管理拓扑塞进玩家 database，也不新建一个业务进程。成功提交回执必须等待所声明的持久级别完成；日志需支持幂等重放、校验、截断尾记录和单写者锁。现有玩家 PersistJournal 只能借鉴，不能未经验证直接宣布满足管理事务和断电恢复。

首阶段支持同一持久卷上的单活动 World 停止后重启，不承诺跨机自动热备。新 World 必须确认旧管理进程已停止，恢复相同记录并提高管理代次，再向 cell 拉取分配清单逐项对账。不能只凭 cell 自报重建提交历史；记录缺失、版本冲突或源端隔离不明的活动保持冻结。管理记录不可用时拒绝新分配，不用空日志顶替旧记录启动。

本地监督模式还必须实现遗留进程重新关联和监督接续；仅有父子进程启动并不提供 World 连续升级。没有这项能力时只能明确停机升级，不能让新管理进程盲目杀掉或复制现有 cell。

有计划更新时先停止新创建与迁移，排平或记录在途操作，完成管理日志交接；旧 World 退出后新 World 接管并重新关联 cell。若 cell 已有活动要持续 tick，整个切换必须在已验证的宽限期和授权范围内完成，否则按失联策略冻结。活动短暂停顿与客户端 TCP 断开是不同验收项。

对账的记录格式（journal v2）、协议扩展（963 cell_space_report）与逐项裁决细化见 [World 重启对账设计](./world-reconciliation.md)（设计稿，评审中）。

## 7. 完整 Space/Instance 迁移

首阶段上线可只做新 Space 分配及自然排空，**不能据此宣称连续热更新完成**。支持活动连续需要下列完整交接。

1. World 预留目标容量，验证协议、玩法资源与快照转换能力，记录迁移 ID 和预期源分配。
2. 源 cell 在 tick 边界冻结迁移单元，记录最后执行的输入序号；排平或记录已发出的 Base 请求及待确认结算，不再制造新副作用。
3. 源导出实体、怪物、Instance 目标/阶段、模拟时钟、随机源、计时器、可序列化脚本状态、输入水位和待办。不能序列化的活动明确拒绝连续迁移，不靠复制 Lua 内存指针恢复。
4. 目标校验快照版本与摘要，恢复为未激活状态；准备成功不推进 tick、不发奖、不产生权威下行。
5. World 确认源已冻结，持久提交唯一目标与新模拟代次。目标凭提交决定激活；目录/gateway 更新版本化路由，源保持冻结直至删除。短暂旧路由明确返回迁移中或过期，不无限转发。
6. 目标按输入序号去重、恢复处理并确认；源清理后释放容量，World 记录完成。提交前取消必须确认无提交决定；提交后不能仅凭超时回滚源。

第一版连续迁移以完整 Space 及其关联 Instance 为单元；若玩法共享状态跨多个 Space，必须整体交接该依赖集合，或暂不支持该活动迁移。普通跨服入场只迁玩家进入另一 Space，不要求搬走整个源活动。

输入缓冲有容量和期限，满载显式拒绝。是否可重放取决于请求序号和执行水位，不能盲目重试非幂等指令。冻结前已执行的结算可能迟到，Base 应按可信提交历史、稳定结算 ID 与已授权操作范围验证，不能简单把所有旧模拟代次的结果都丢弃，也不能允许旧端继续生成新结果。

## 8. 跨服与两种更新

共享玩法由目标 World 分配自己的 cell，玩家仍使用各自原 Base。目标解析 Base 服务身份，不获取小服数据库地址/凭证；Base 升级改变服务代次，不改变原服和存储归属。

跨 World 玩家迁移，由源 World 为本次操作持有唯一持久提交记录，目标 World 先预留和准备，遵循该决定激活；源协调端不可达时不擅自取消或双端恢复。接收端保留决定凭据和完成记录，结果不明查询同一迁移 ID。暂不支持把整个 Space 的管理归属在两个 World 间在线转移；这需要另行定义管理记录和未完成操作的交接。

| 更新方案 | 所需能力 | 能力边界 |
|---|---|---|
| 支持协议更新的进程替换 | 新旧进程并存、实际新旧解码/适配、快照转换、上述冻结/提交/路由流程 | 内部协议与客户端协议分别校验；客户端未升级时仍须旧协议兼容层，不能靠 schema 白名单实现 |
| 只更新代码、wire 不变 | Lua 在安全执行点更新并处理私有状态/旧协程；C++ 替换 cell 时复用相同迁移流程 | Lua 原地更新不等于任意运行状态可迁移；C++ 换进程仍需快照与权威交接 |

Base 更新交接长期对象与存储写权，World 更新交接管理记录，cell 更新交接模拟状态，三者分别实现。gateway 不替换时可保持客户端 TCP，但模拟可能短暂停顿；gateway 自身替换仍需独立的连接交接或重连设计。

## 9. 无缝地图兼容边界

现在必须保留稳定 Space/实体 ID、全空间坐标、显式 Cell 范围/邻接、分配版本和单实体模拟代次；不能用执行进程 ID 当 Space ID。现有 Scene 继续承担本地模拟容器，后续把其本地范围与逻辑 Space 身份分开，不叠加 Scene→Space 同义容器链。

未来同 Space 多 Cell 时，需要增加 Real/Ghost 复制、跨边界 AOI/Witness 连续、实体逐个移交、跨 Cell 战斗裁决和 Instance 共享状态唯一负责人。首阶段可以全 Space 统一迁移代次；契约还须能为实体保留独立权威代次，不能永久假定它们相同。

现有 SceneTransfer 离场后重建 Avatar，可复用显式换空间部分原语；同 Space 跨 Cell 必须保留实体 ID、血量、冷却、计时和观察连续性。上述接口为扩展提供空间，**不构成已经支持无缝地图的证明**。

## 10. 明显风险与评审意见

| 问题 | 不合理的做法 | 本案建议 |
|---|---|---|
| 为轻量玩法引入过多分布式能力 | 第一版就做分区平衡、Ghost 和自动故障接管 | 先共用二进制分角色、自动启停、单 Cell/多 Space 和自然排空；接受控制故障时短暂停顿 |
| World 成为热点 | 所有移动/战斗/可见性都经 World 代理 | 业务直连 cell；控制请求有界，心跳汇总，迁移/快照限速 |
| 网络分区双模拟 | 心跳超时就复制玩家并激活目标 | 源冻结或可验证隔离后提交，结果不明保持冻结 |
| World 成为故障点 | 只有内存拓扑，重启相信执行端自报 | 独占管理、持久决定、清单对账；首版不承诺自动热备 |
| 迁移活动不完整 | 只搬 Avatar，重建怪物/随机源/脚本 | 完整依赖快照，不能支持的玩法明确拒迁 |
| 跨服越权或重复结算 | cell 直写各服数据库，单靠当前代次判结果 | 原 Base 验证，稳定结算 ID、授权历史和持久去重 |
| 管理日志与存储承诺不符 | 普通文件 flush 就宣称断电无损 | 写清持久级别，验证崩溃点，缺失记录拒绝自动恢复 |

仍需评审后再定的实施参数：管理日志持久级别、心跳/宽限期、容量预算、快照大小及停顿预算、各玩法脚本的可迁移状态清单。这些参数没有实测依据前不写成性能承诺。自动接管、管理范围在线转移、同 Space 多 Cell 均单独立项。

### 10.1. 是否需要 interfaces

[KBEngine 官方配置说明](https://kbengine.github.io/cn/docs/installation.html)中的 interfaces 是运营/第三方接入服务，涉及外部账号、登录和计费；[源码声明](https://github.com/kbengine/kbengine/blob/master/kbe/src/server/tools/interfaces/interfaces.h)包含账号创建、登录及 charge 请求/回调。它不等于客户端 gateway，也不属于 World 的模拟管理。

Apollo 先预留异步接入接口，不列为默认必启进程。简单的平台登录验证可先由 login 的适配模块完成，限制超时、并发和积压；外部慢请求不能阻塞认证循环，更不能进入模拟 tick。将来有多渠道、支付回调、独立密钥或部署隔离需求时，可采用 `apps/interfaces` / `interfaces` 承载外部协议适配，不另造名称。

独立后，interfaces 负责验签、外部身份映射、格式转换和有界转交；login 决定游戏登录与会话，base 决定业务奖励和消费，database 持久化。接口回调的订单/事件 ID、重试与持久去重必须全链路定义；若已向外部确认受理，应有可恢复的交付记录，不能仅把消息留在内存。interfaces 不直接修改玩家资料、不推进模拟、不获得各小服存储凭证。此项是可选方案，启用和支付业务设计另行评审。

## 11. 当前代码与实施顺序

| 当前实现 | 拆分时的归属/缺口 |
|---|---|
| WorldApp::gameLoop、acceptanceQueue_、WorldHost、World/Scene | 模拟循环与有界意图消费迁入 cell，沿用单写者和停机尾扫 |
| WorldApp 的 PlayerStore、Anchor 与结算直连 | 完整资料与长期写权移回 Base；cell 接只读快照及远程业务接口 |
| SquadInstanceService、Instance | 活动运行归 cell；空间选择改为 World 预留/提交，不能跨进程继续持本地指针 |
| WorldAssignment | 尚缺完整 Cell/执行进程/管理和模拟代次；现有字段不能证明新路由契约已完成 |
| SceneTransfer、现有 World 间档案迁移 | 拆出显式换空间；禁止把完整档案搬迁当作 Base 固定的新模拟迁移 |
| M1、目录和 machined | 复用传输与监督原语；补认证注册、真实 wire、幂等命令与授权校验 |

建议顺序：先完成 Base/模拟长期数据边界；再落地同一二进制的 World/cell 角色、本机监督、注册、完整 Space 创建/回收和故障冻结；再支持多 cell 分配与有上限的自动扩缩容；最后补管理恢复、完整活动迁移及两种更新验收。迁移未完成前只能使用自然排空升级，不能勾选连续热更新完成。

本案不改程序、C++ 类型和协议字段，不自动接受新决策；唯一实施清单仍是根目录 todo.md，评审后按本案补齐其中 P2/P3/P4/P5 的验收条件。

## 12. 启用验收

- 共用二进制两个角色真进程启动；cell 角色不递归派生，启动失败有限退避，缩容退出不被误重启；
- 单 World/单 cell 真进程启动；没有 cell 时明确不可创建；World 不再推进模拟或加载完整档案。
- 高低水位、冷却、启动中计数、资源上限、自然排空、长驻 Space 阻塞缩容和 World 重启不重复派生得到验收；
- 两 cell 并发创建、多 Space 隔离、容量预留/拒收、重复请求、回执丢失、迟到销毁都有确定结果。
- 重启代次、伪造注册、World/cell 失联、进程暂停再恢复及旧输入/旧下行被拒绝，不出现双权威。
- World 在创建/迁移每个持久提交点前后崩溃，恢复后决定一致；日志损坏/丢失不静默创建新权威。
- 连续迁移保持成员、怪物、目标、血量、技能、时钟、随机和必要脚本状态；覆盖准备/提交不明、目标失败和源清理失败。
- 两区服原 Base 不变；结算 ACK 丢失、重复/迟到结果、Base 不可达和重启不重复发奖，未确认记录不提前删除。
- 新旧真实协议解码/快照转换与仅代码更新分别演练；活动停顿、免重登和 TCP 连续分别记录。

# Apollo Core Glossary (concept-glossary)

> Status: the terminology authority carrier (a registry document, rolling additions as rulings land). Positioning: organize **general architecture concepts** into one table — each entry gives three things: **general meaning / which engines have it / apollo's counterpart and stance** (with authority-carrier pointers). Later design and analysis documents cite this table's entry names instead of re-defining from scratch; new concepts **enter this table before landing in documents**. Cutoff date 2026-09-30.

## 0. Usage and Ruling Records

**New-word rules (strict, user order 2026-10-12)**
1. **Check existing words first**: before fixing on any term, the first step is to check whether BigWorld and KBEngine already have a word for it — if an existing word exists, use it, always; no coining alongside.
2. **New words need a reason**: only when neither has one may a new word be coined, and it must come with a one-line "why the existing words are not enough".
3. **Unapproved = pending**: before user approval, new words are always marked **pending (待定)** and do not enter design documents or code.
4. **Approved entries cite their source**: no entry in this table may say "user-approved" unless the source can be found in git log or session records — if found, write the commit hash or date; if not, write "source unknown".

**Citation usage**
- Citation format: "entry name (concept-glossary)"; cross-engine comparisons defer to this table, no re-pasting of line numbers.
- Inclusion criteria: **general concepts** shared by multiple engines/industry, or apollo-coined words that are easily confused; mechanism parameters and implementation details belong to the individual design documents — this table only fixes boundaries.
- Cross-engine line numbers in the table are read-on-record from local working copies of the three repos (dual-track semantics as deep-dive §0); apollo carrier pointers roll with the design documents, `docs/design/*` is authoritative.

**Terminology ruling records (2026-09-30, user instruction)**
1. **Battle → instance naming** (two items): ① docs/25's "Battle Service" really means **副本 (instance)**, not "battle" — that name is **voided**; later documents always write "**副本**" (English/code identifier = **instance**; alias dungeon; colloquial in tower-defense/arena contexts = room). ② **The word "battle/战斗" is reserved for the battle-logic domain** (battle verification / battle settlement — see the "battle verification service" entry) and is no longer used in any spatial/instance naming. Corresponds to the KBEngine `Space` concept; the deleted docs/25 is traceable via `git show 1e37073d^:docs/25-Battle_Service_Design.md`.
2. **No registry introduced**: no etcd/consul-style external registry; the sole semantics for process discovery = **G-1 dual layer** (machined daemon + UDP broadcast, net-abstraction §7). The registry-source document docs/05 §2.3 was deleted whole with the ruling (git-traceable), and row #13 of doc 36 was rewritten in sync.
3. **No ghost** (decision #9, registered 2026-09-29): cross-baseapp migration goes through explicit handoff; remote visibility goes through RO_MIRROR read-only mirrors.

## 2. Key Disambiguations (easily confused pairs)

### 2.1 scene vs instance vs baseapp — three granularities, each manages its own

- **scene** = the data-and-logic unit: entity container, AOI boundary (sceneId).
- **instance (副本)** = the **lifecycle form** of a scene: instantiated when gameplay opens, destroyed when it ends; may be placed on a separate process (apollo's instance process), in KBE it is just another `Space` entity (space itself is a scriptable entity).
- **baseapp** = the **process unit**: the game-logic server process carrying one or more scene/instance — the granularity of fault domain and scale-out.
- One sentence: **scene is "a piece of world", the instance is "one run of a piece of world", baseapp is "the machine slot the world runs on"**.
- Player-object same-axis closure (2026-10-03): **the anchor is on Base (Home baseapp, never moves), spatial state is on Cell (lives and dies with the scene)** — three-layer duties and the scene-transfer/disconnect/reconnect rules see player-object-model (gap #18); **object layering ≠ process layering**, three layers co-resident on baseapp.

### 2.2 ghost vs RO_MIRROR — different names because different stances

ghost serves the **seamless world**: neighboring-process bidirectional projection, double-write, call forwarding — the shape apollo's decision #9 rejected; RO_MIRROR is the **one-way read-only mirror** apollo keeps: for hot-standby streams and read-only views, writes are always only at the owner, call forwarding goes to the authoritative side — the landing of "sharing = subscribing to the owner's projection" (net-abstraction §7 sharing model) on mirror-type information. So apollo did not "rename ghost" — it **changed the synchronization model**.

### 2.3 Service discovery vs registry — fact acquisition vs external ledger

Discovery answers "who is alive, where" (apollo: daemon + broadcast, eventually consistent); a registry is an external strongly-consistent ledger (etcd/consul, leases + watch). The basis for the no-introduction ruling: small process topology, low-frequency changes — strong consistency buys no matching return (net-abstraction §7 G-1); the cross-subnet gap of broadcast is filled by the **single-machine daemon** — machine-level liveness and launching should never have relied on broadcast anyway (deep-dive §13 post-ruling reading). Note that in KBE parlance "注册中心" mostly means **engine-internal** management components like machine/mgr (qa q28), not the same thing as a microservice registry.

### 2.4 The two layers of heartbeat

Connection heartbeat (byte layer: RTO/timeout → disconnect-reconnect resume) and logic heartbeat (tick layer: version unchanged = stalled) must not be mixed — the former is handled by the transport/session layer (may kill the connection), the latter only alarms without killing (skynet monitor, same shape). apollo's two layers each have an owner (§1.4 last row); detection and recovery are also two things: G-5 only emits signals, handling belongs to the baseappmgr recovery phase.

### 2.5 login_token vs session_key vs resume token — three credential layers, each covers one segment (2026-10-01, landed with login-flow)

| Credential | Domain | What it governs | Issuer/negotiator | Lifetime |
|---|---|---|---|---|
| **login_token** | account domain | one-time **entry ticket**: proves "authentication passed, admission approved" — gateway verifies locally, baseappmgr redeems in the critical section | issued by login-app (HMAC-SHA256 self-contained) | short TTL (60s suggested) + one-time (nonce redemption) |
| **session_key** | connection domain | the **frame-encryption key**: negotiated by the ClientHello/ServerHello handshake, fed to CryptoFilter to encrypt all frames | negotiated per connection by both sides (X25519+HKDF, net-abstraction §5.9) | new per connection — resume reconnection also redoes ECDH, **the old key is not restored** |
| **resume token** | session domain | the **disconnect-recovery credential**: proves "I am that session just now" — restores L2 seq/queue state on reconnect | sent by the server when the game connection is established (L2) | TTL **same source, one value** with the disconnect grace window (session-and-online-directory §4) |

The three layers are mutually non-interchangeable and non-derivable (key hierarchy net-abstraction §5.9 :317, credential plane): whoever steals a resume token cannot produce a session_key (must redo the handshake), reconnecting with an old session_key is rejected (nonce freshness), a login_token used a second time is rejected (nonce already redeemed) — each layer's compromise is sealed within the layer.

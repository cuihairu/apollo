
# World 模拟线程与写入边界

本文说明副本模拟状态的单写者纪律，并区分目标模型与当前对局原型的实现。目标命名以[概念词汇表](./concept-glossary.md)为准。

## 目标规则

每个 Instance 的权威模拟状态由一个逻辑线程顺序修改。网络 IO、管理请求和后台工作线程只能提交带关联 ID 的意图；World 在模拟边界验证并执行意图，再返回结果。此规则让一场对局的状态变化有明确的顺序，也避免多个线程同时改写 Entity、Scene 或 AOI。

多个 Instance 可以由同一个 World 的调度线程承载，也可以由多个互不共享可变状态的模拟线程承载。线程分配属于实现和容量决策，不改变 Instance 的单权威规则。

## 当前代码行为

现有 `world-app` 原型使用 `WorldApp::gameLoop` 作为 `World` 的写入线程。M1 链路由该循环泵送，回调将意图放入有界 `acceptanceQueue_`；循环在固定位置消费意图、运行 Lua 接线并调用 `WorldHost::tick`。停止接收后，循环会执行一次尾部队列 drain，再拆除脚本宿主。源码类名保留在实现映射中；此进程的目标职责是 World。

当前原型启动时创建一个默认 `Scene` 和一个 `Instance`。底层 `World` 有创建其他场景的 API，Instance 已有八态生命周期；当前缺口是应用层的小队触发创建、分配、通关结算和资源回收流程。因此不能把现有 `Scene` 或 `Instance` 直接宣称为完整 World 实现。

## 过载与停机

队列满时拒收新意图并返回过载结果，不静默丢弃已接收的意图。停机顺序是关闭受理、让模拟线程完成尾扫、停止链路和宿主。生产停机还需定义 drain 上限、未完成请求的失败回执及进程强杀的恢复行为；这些行为需纳入根目录 [`todo.md`](https://github.com/cuihairu/apollo/blob/main/todo.md) 的验收项。

## 并发验收

- 网络泵送和后台任务不得直接改写副本模拟状态。
- 对每个 Instance 的输入有可复现的消费顺序，重复请求不会重复执行非幂等写入。
- 队列达到容量上限时有可观察的拒收结果和指标。
- 正常停机时已受理工作按约定完成或返回明确失败；超时强停时可恢复或判定对局失败。
- 测试覆盖队列满、重复请求、停机竞态和模拟线程异常。

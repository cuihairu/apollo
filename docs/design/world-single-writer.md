# 模拟线程与写入边界

目标执行职责属于 cell；worldServer 管理 Space/Cell 拓扑。此文件路径保留，避免为了职责调整反复改名。当前 WorldApp 代码是管理与执行尚未拆分的实现，见[体系对照](./bigworld-apollo-mapping.md)。

## 目标规则

每个实体在任一时刻只有一个权威 Cell 写入者。Cell 的逻辑执行者顺序修改本地实体、AOI 与模拟状态，IO、后台工作和调试入口只能投递有界意图。一个执行进程可承载多个 Space 的 Cell，不能据此把 Space 或 Instance 定义为进程。

默认单 Cell 承载一个 Space 的模拟。未来一个 Space 多 Cell 时，各分区独立执行，跨区操作交给实体权威方裁决；同一 Instance 的共享目标、计时与结算需唯一逻辑负责人，不要求所有分区共享内存或全局锁步。长期资料仍由 Base 修改，database 验证并持久写入，不通过模拟线程获取资料写权。

## 当前代码行为

现有 WorldApp::gameLoop 泵送 M1，将意图放入 acceptanceQueue_，在固定边界消费、执行 Lua 并调用 WorldHost::tick。关闭受理后尾扫队列，再拆除宿主。迁移时将模拟循环放入 cell，worldServer 留下管理职责；不把现有类名当成目标部署事实。

## 过载与停机

队列满时显式拒收，不静默丢弃已受理意图。关闭新受理后完成尾扫、停止模拟与链路；排空须有期限、结算策略、失败回执与强停恢复定义。受理、执行和持久成功分别确认。

## 并发验收

- IO 与后台任务不直接修改模拟对象；每个实体只有一个有效权威代次。
- 输入消费顺序可追踪，重复请求不重复产生业务写入。
- 队列满、停机竞态、执行异常与强停有明确结果。
- 迁移目标提交前不执行，提交后源端被隔离；共享 Instance 状态不产生双负责人。

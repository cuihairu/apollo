# Q33: 如何处理热点数据？

## 问题分析

本题考察对热点数据处理的理解：
- 热点数据的定义和危害
- 缓存策略
- 数据分片
- 多级缓存架构

## 一、热点数据问题

### 1.1 什么是热点数据

```
┌─────────────────────────────────────────────────────────────┐
│                    热点数据定义                                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  热点数据: 被频繁访问的数据                                  │
│                                                             │
│  MMO 中的热点数据:                                          │
│  ├── 玩家基本信息 (登录时频繁查询)                          │
│  ├── 排行榜 Top 数据 (大量玩家查询)                         │
│  ├── 热门道具价格 (交易行查询)                              │
│  ├── 系统配置数据 (频繁读取)                                │
│  ├── 公会信息 (成员频繁访问)                                │
│  └── 活动状态 (活动期间高频查询)                            │
│                                                             │
│  问题:                                                     │
│  ├── 数据库压力过大                                        │
│  ├── 响应延迟增加                                            │
│  ├── 可能导致数据库宕机                                     │
│  └── 影响玩家体验                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 热点数据分类

| 类型 | 示例 | 访问特点 | 解决方案 |
|------|------|----------|----------|
| **读多写少** | 配置、排行榜 | 高频读取 | Redis 缓存 |
| **读多写多** | 金币、积分 | 高频读写 | Redis + 队列 |
| **读写均衡** | 背包、装备 | 中频访问 | 分表 + 缓存 |
| **突发热点** | 活动数据 | 短时高峰 | 预热 + 扩容 |

## 二、缓存策略

### 2.1 多级缓存

```
┌─────────────────────────────────────────────────────────────┐
│                    多级缓存架构                                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  L1: 进程内缓存 (单机)                                     │
│  ┌─────────────────────────────────────────────────┐       │
│  │  - 存储在进程内存中                                  │       │
│  │  - 访问速度最快 (<1ms)                              │       │
│  │  - 容量有限 (MB 级别)                              │       │
│  │  - 多实例数据不一致                                 │       │
│  │                                                   │       │
│  │  适合: 配置数据、静态表                             │       │
│  └─────────────────────────────────────────────────┘       │
│                          │                                  │
│                          ▼                                  │
│  L2: Redis 缓存 (分布式)                                  │
│  ┌─────────────────────────────────────────────────┐       │
│  │  - 分布式共享                                      │       │
│  │  - 速度快 (~1-5ms)                               │       │
│  │  - 容量大 (GB 级别)                               │       │
│  │  - 支持过期策略                                    │       │
│  │                                                   │       │
│  │  适合: 玩家数据、排行榜                             │       │
│  └─────────────────────────────────────────────────┘       │
│                          │                                  │
│                          ▼                                  │
│  L3: 数据库 (持久化)                                        │
│  ┌─────────────────────────────────────────────────┐       │
│  │  - 数据最终存储                                    │       │
│  │  - 速度慢 (~10-100ms)                             │       │
│  │  - 容量最大 (TB 级别)                              │       │
│  │                                                   │       │
│  │  适合: 所有数据的持久化                             │       │
│  └─────────────────────────────────────────────────┘       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Cache-Aside 模式

```cpp
// Cache-Aside 缓存模式

template<typename T>
class CacheAside {
public:
    // 获取数据
    T get(const std::string& key) {
        // 1. 先查缓存
        T value;
        if (cache_.get(key, value)) {
            // 缓存命中
            return value;
        }

        // 2. 缓存未命中，查数据库
        value = database_->load<T>(key);
        if (value.isNull()) {
            return value;
        }

        // 3. 写入缓存
        cache_.set(key, value, cacheTTL_);

        return value;
    }

    // 更新数据
    void set(const std::string& key, const T& value) {
        // 1. 更新数据库
        database_->save(key, value);

        // 2. 更新缓存
        cache_.set(key, value, cacheTTL_);

        // 3. 删除其他服务器的缓存（如果需要）
        invalidateOtherCaches(key);
    }

    // 删除数据
    void remove(const std::string& key) {
        // 1. 删除数据库
        database_->remove(key);

        // 2. 删除缓存
        cache_.del(key);

        // 3. 通知其他服务器
        invalidateOtherCaches(key);
    }

private:
    void invalidateOtherCaches(const std::string& key) {
        // 通过 Redis Pub/Sub 通知
        redis_.publish("cache:invalidate", key);
    }

    Cache& cache_;
    Database* database_;
    uint32_t cacheTTL_ = 300; // 5分钟
};
```

## 三、数据分片

### 3.1 分片策略

```cpp
// 数据分片路由

class DataSharding {
public:
    // 获取分片
    size_t getShard(uint64_t playerId, size_t shardCount) {
        // 一致性哈希
        return hash(playerId) % shardCount;
    }

    // 获取分片数据库
    Database* getShardDatabase(uint64_t playerId) {
        size_t shardId = getShard(playerId, shardCount_);
        return databases_[shardId];
    }

    // 查询玩家数据
    PlayerData getPlayerData(uint64_t playerId) {
        Database* db = getShardDatabase(playerId);

        auto result = db->query(fmt::format(
            "SELECT * FROM player_{} WHERE id = {}",
            getShard(playerId, shardCount_), playerId
        ));

        if (!result.empty()) {
            return parsePlayerData(result[0]);
        }

        return {};
    }

private:
    size_t hash(uint64_t key) {
        // MurmurHash 或 FNV
        return std::hash<uint64_t>{}(key);
    }

    std::vector<Database*> databases_;
    size_t shardCount_ = 4;
};
```

## 四、缓存更新策略

### 4.1 更新策略对比

```
┌─────────────────────────────────────────────────────────────┐
│                  缓存更新策略                                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Cache-Aside (推荐):                                       │
│  ┌─────────────────────────────────────────────────┐       │
│  │  读: 先读缓存，miss 再读 DB                          │       │
│  │  写: 先写 DB，再更新/删除缓存                       │       │
│  │                                                   │       │
│  │  优点: 简单、可靠                                    │       │
│  │  缺点: 可能短时间不一致                               │       │
│  └─────────────────────────────────────────────────┘       │
│                                                             │
│  Write-Through:                                            │
│  ┌─────────────────────────────────────────────────┐       │
│  │  写: 同时写缓存和 DB                               │       │
│  │  读: 先读缓存                                       │       │
│  │                                                   │       │
│  │  优点: 强一致性                                     │       │
│  │  缺点: 写入延迟大                                   │       │
│  └─────────────────────────────────────────────────┘       │
│                                                             │
│  Write-Behind:                                             │
│  ┌─────────────────────────────────────────────────┐       │
│  │  写: 先写缓存，异步写 DB                             │       │
│  │  读: 先读缓存                                       │       │
│  │                                                   │       │
│  │  优点: 写入速度快                                   │       │
│  │  缺点: 可能丢失数据                                   │       │
│  └─────────────────────────────────────────────────┘       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 五、总结

### 热点数据处理方案

| 方案 | 适用场景 | 复杂度 |
|------|----------|--------|
| **Redis 缓存** | 读多写少 | 低 |
| **本地缓存** | 配置数据 | 中 |
| **数据分片** | 大量玩家 | 高 |
| **读写分离** | 查询多 | 中 |

### 最佳实践

```
1. 多级缓存降低 DB 压力
2. 合理设置 TTL 避免雪崩
3. 分片分散热点
4. 监控热点数据
5. 预热准备热点数据
```

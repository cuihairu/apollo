# Can Apollo Be More Complete Than BigWorld? An Auditable Assessment

> Scope: compare Apollo's fit and verifiability for instance-based multiplayer game servers, not total product features or historical production scale. This is an engineering note. “Can exceed” means a measurable direction, not a claim that Apollo already exceeds BigWorld. Repository status was checked against current `main`; external sources retrieved 2026-10-19.

## Conclusion

**Apollo can become a better fit and provide stronger evidence in selected dimensions; there is no basis today to claim that Apollo is more complete overall.** Public BigWorld material shows distributed Cells, Ghosts, CellAppMgr, and load adjustment. Apollo focuses on instance-based gameplay, deterministic verification, and engineering observability, while reserving boundaries for future multi-Cell operation. These are different goals and require separate acceptance evidence.

## Acceptance matrix: minimum falsifiable evidence

Retain the input, environment, rule, and result for each experiment. A failure disproves the corresponding “exceeds” claim; documents and diagrams alone are insufficient.

| Dimension | Minimum acceptance form | Falsification condition |
|---|---|---|
| A1 Instance lifecycle | Full transition table, repeated settle/destroy, and post-failure ledger reconciliation; assert unique rewards and cleared terminal resources. | An illegal transition succeeds, a reward is duplicated/lost, or an active instance cannot converge to terminal state. |
| A2 Deterministic replay | Repeat with fixed binary/seed/snapshot/input; change one input and identify the first per-tick hash divergence. | Same input produces different hashes or an intentional change cannot be localized. |
| A3 Capacity/regression | Rerunnable workload, hardware/compiler parameters, raw samples, and p95/p99/throughput/dropped-tick/queue report; same-basis BigWorld comparison. | Cannot reproduce, critical data is missing, target metric is not better, or variance exceeds declared bounds. |
| A4 Fault diagnosis | Same injection list with dump, symbolized stack, generation, correlated logs/metrics, and recovery decision; compare item by item. | Missing crash evidence, unusable stack, uncorrelated generation, or state/settlement error during recovery. |
| A5 Protocol governance | Automated old/new protocol matrix, rolling upgrade, unknown fields, reconnect behavior, plus trace/alert records; compare equivalent BigWorld scenarios. | Valid old clients are silently misread, upgrades misroute messages, or faults cannot be diagnosed. |

## Recommended order (pre-decided)

**First complete A1/A2 automated tests and durable settlement/recording evidence → establish A3/A4 baselines (measurement and fault records) → close A5 protocol compatibility and observability → separate World/cell and implement static multi-Cell → Ghost/Witness and boundary AOI → fenced migration/takeover → automatic balancing and large-scale soak comparison.**

Migration and automatic balancing depend on topology identity, single-writer authority, replayable state, capacity telemetry, and fault reconciliation. Expanding distributed runtime before these are evidenced makes correctness hard to prove. The first four items improve verifiability for Apollo's instance-based target; multi-Cell is later work to catch up with BigWorld's spatial runtime, not a present advantage.

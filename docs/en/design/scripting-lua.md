
# Apollo Lua Scripting Layer Design (scripting-lua)

> Status: design draft (under review). Forward-looking basis: the repo planning (docs/qa/q101-script-language.md etc.) has already settled the scripting-language direction on Lua. This design cross-references `docs/analysis/architecture-review.md` (container division of labor), `docs/design/attribute-sync.md` (attribute hooks/formulas), `docs/design/net-abstraction.md` (async return to the main thread), and `docs/design/sdk-contract.md` (client contract).

---

## Executive Summary

1. **The division of labor in one sentence: the dynamic goes to Lua, the hard-real-time goes to C++.** Gameplay logic (quests/skill behavior trees/AI/formulas/drops) goes into Lua in exchange for hot updates and designer self-service; network send/receive, attribute storage/sync, AOI, ECS, and persistence stay in C++. This boundary determines all the interface design below.
2. **C++ services open to Lua only "named module tables injected at startup"** (`apollo.attr`/`apollo.db`/`apollo.scene`); binding is validation, and anything missing errors at startup — **scripts are forbidden from reverse-looking-up the service container by name** (the string-lookup defect of architecture-review.md P0-1 must not be replicated in the scripting layer).
3. **Hot-replacement protocol**: worker threads preload + compile → the main thread swaps the table once atomically at a tick boundary → on failure, roll back to the old table; modules carry version and dependency declarations, canary first (a single scene trial-run). There is no runtime add/remove of C++ beans (the C++-side runtime register/unregister APIs are removed along with architecture-review).
4. **Attribute hooks have a single integration point**: `onAttrChanged(entity, id, old, new)` sits in the attribute pipeline's "after recalc, before broadcast" phase (attribute-sync.md §10, between tick phases 2/4); a whitelist bitmap plus an instruction budget keeps scripts from dragging down broadcasts; scripts are read-only on the "final visible value" and make final adjustments only on the whitelist.
5. **The formula system moves from C++ into Lua functions**: the self-built expression-compilation scheme of docs/03 is abandoned; derived-attribute formulas = Lua functions + the dependency graph stays in C++ (recalc scheduling does not depend on the script engine).
6. **Sandbox**: no io/os tables, instruction-count budget/frame, memory cap, per-entity script time-slice round robin; script exceptions are contained (error → log + entity behavior fallback), never crashing the process.
7. **The runtime carrier of contract semantics (sdk-contract §10.6 v3, added 2026-09-29)**: the data for business-message handler binding and the attribute-write whitelist comes from `contract.lua` (the Lua contract table emitted in the same generator batch: attr table/message routes/whitelist) — loading and hot updates go through the same table-swap protocol as §3.2; the entire business surface of "zero C++ recompiles on server contract change" is carried on the Lua side (see §3.4).
8. **Online debugging and performance attribution (§7, added 2026-09-29)**: attach execution = **single admin entry + control-channel forwarding + tick-boundary sandboxed eval** (KBE telnet / skynet debug_console precedents; permissions split into Passive Query / Controlled Action); the Lua state surface's four inventories (memory GC / coroutines / module versions / env sampling) hang off the observability tree's `/script` branch; performance attribution = the dual-role instruction hook (budget enforcement + per-module time accounting) + external sampling on the C++ side (perf/Tracy class, not self-built); infinite-loop detection already exists in §6 (naturally covered by the instruction budget); **no breakpoint-style debugger** (single-writer thread freeze + tick-determinism destruction).
9. **Async task model and hot-update hardening (§3.5/§8, added 2026-09-29)**: the async wrapper under single-writer threads = **C++-side callbacks + request_id handoff, Lua-side coroutines** (the §8.1 comparison table rules out introducing future/promise — std::future's blocking get violates tick discipline, and JS Promise's microtask semantics are obtained in a simpler form via "coroutines + tick-boundary resume"; the skynet.call coroutine paradigm precedent skynet.lua:227); three disciplines = resume only at boundary points / re-validate after resume / timeout upper bound + cooperative cancellation. Four hot-update additions (§3.2): persisting the current-version pointer (against a bad-version crash loop), coroutine upgrade semantics (old coroutines finish on the old table), canary granularity per scene thread, and the zero-migration discipline for module-private state; §3.5 bytecode cache (build-time precompilation + manifest-triple verification, Lua version header against mis-loading); §2 adds the Lua 5.4 version lock (sol2 fully supports it; LuaJIT re-evaluated only on measured bottlenecks).
10. **Binding layer and version decisions (revised 2026-09-30, version policy re-revised the same day)**: sol2 is dropped (upstream maintenance stalled — the double risk of heavy-template compilation cost + strong coupling to Lua version upgrades); **a thin native Lua C API binding** (`luaL_Reg` function tables + userdata wrapping, a few hundred lines — the small binding surface is the precondition); **the Lua 5.5 line, version following vcpkg** (first pinned 5.5.1, then re-revised the same day to "lock the 5.5 main line, patch position follows the vcpkg lua port, currently 5.5.x" — no self-pinned patch versions, no self-maintained overlay ports; minor-version upgrades are still explicit batches; no 5.4 intermediate state is landed; the number = int64/double semantics unchanged, the battle-determinism determinism discipline is unaffected); sdk-contract's "sol2 bridge" is renamed in sync to "C-API transfer bridge" (its §10.6 sub-section update note — the bridge was always self-written code; dropping sol2 only swaps the transfer function family).
11. **GM/operations command surface (§7.5, added 2026-09-30)**: registry-driven command table (`gm_commands` declarations + parameter schema validation — no eval permission on the GM surface); write permission = the contract.lua `gm_write` independent whitelist (listed separately from `predict`; writes go through the attribute-hook route, no pipeline bypass); three-tier level grading + two-person review for high-risk (business granularity above the framework's AccessController); the standalone `gm_audit` audit table (wall+tick dual-write, rejections also recorded); GM input = the admin session's intent stream (automatically included in battle-determinism recomputation); the pipe is the same as attach, zero additions.
12. **Fault notification contract (§6.1, added 2026-09-30)**: three event levels (WARN soft-threshold debounce / FAULT abort + fallback / TRIP circuit-breaker trip) → the cold-path single point `onScriptFault` (one fixed C++ function slot per state, non-virtual, no registry, three O(1) actions: ERROR bypass log + MetricRegistry counter + the circuit-breaker state machine); **the engine provides no script-implemented fault SPI** (the watchdog must not depend on the watched / hot-path callbacks violate tick discipline / pcall self-handling is already a business channel); module-level circuit breaking (3 faults/1000 ticks → 600-tick quarantine, half-open doubling, auto-reset on hot-update version change); ScriptFaultEvent fields closed, wall+tick dual-write; external dispatch (webhooks etc.) is entirely on the exporter side (logging §5.2) — synchronous IO/HTTP/cross-process calls are forbidden on the fault path.

## 1. Positioning: Where the Boundary Is

| Dimension | C++ (host layer) | Lua (gameplay layer) |
|---|---|---|
| Responsibilities | transport/storage/attribute authority/sync/scene and AOI/ECS/persistence/network | quests, AI decisions, skill logic, formulas, drops, GM validation, UI data assembly |
| Hot updates | restart or version swap via gradual rollout | second-scale hot replacement |
| Attribute-write permission | any attribute (C++ logic, authoritative) | whitelist fields only (§4); otherwise it only sends "intents" |
| Performance discipline | no budget (but locks/allocation garbage forbidden) | instruction budget + per-frame time slice |

The criterion: **does this logic need to change at runtime / be iterated by designers? Yes → Lua; no and high-frequency → C++.** Attribute-value storage itself never enters Lua (multiple dimensions: GC pressure, authority bypass, unclear data ownership during hot updates).

## 2. Host and Runtime

- **One logical thread, one `lua_State`** (reusing `modules/base/thread_pool` is irrelevant here; attach directly to the scene/space thread): state isolation, no interlocking, no OS-related overhead on hot paths; entity data stays in C++, and the Lua side is only a "logical reference" (userdata/lightuserdata wrappers), never a copy of entity state.
- **Binding-layer selection**:
  - **Thin native Lua C API binding (decided 2026-09-30: sol2 dropped)** — upstream maintenance stalled (ruled by the user's verification on 2026-09-30), heavy-template header compilation cost, and strong coupling to Lua version upgrades (a third-party binding library's adaptation to new Lua versions is always a single-point lag); apollo's binding surface is small to begin with (§8's three-piece kit + the `apollo.*` injection tables + attr accessors), and hand-written `luaL_Reg` function tables + userdata wrapping = a controllable few hundred lines, zero third-party maintenance risk. sol2's benefit scenario (large-scale class template binding) does not exist in apollo — once "both suffice" turned risky on the scale, the old trade-off was settled on hand-written.
  - **Lua version-lock discipline (added 2026-09-29; revised twice on 2026-09-30: the 5.5 line, version following vcpkg)**: **lock the 5.5 main line, patch position follows the vcpkg lua port** (currently 5.5.x) — the first embedding lands directly on the 5.5 line, no 5.4 intermediate state (no migration baggage, and with sol2 dropped no binding-library compatibility matrix drags on version choice); the concrete version is not self-pinned, and no overlay port is self-maintained (single dependency source: lua goes through the vcpkg baseline together with openssl etc., per the user's 2026-09-30 instruction). Upgrades split into two tiers: **patch position (within 5.5.x) floats with vcpkg dependency resolution** — within a minor, the bytecode format and C API are stable, with §3.5's manifest version-header verification as the backstop; **minor version (5.5→5.6) = an explicit batch**: the bytecode format header (§3.5), the C API compatibility surface (our own binding layer — compiler-visible for banned APIs), and integer/floating-point semantics (number = int64/double — battle-determinism §2 determinism discipline) all move together with the version, with regression verification, never silently via dependency resolution. The LuaJIT fallback is constrained (language subset of the 5.1 line + some 5.3 extensions, bytecode not interchangeable with PUC Lua) — PUC Lua by default; LuaJIT is re-evaluated only when §7.3 attribution measurements put the bottleneck in the VM (measure first, then switch, same discipline as "no self-built profiler").
  - No over-optimization "for performance": the cross-boundary call-frequency ceiling is a few intent calls per entity per frame, far below intra-C++ call rates; the truly high-frequency paths (attribute setting, movement) are not allowed through scripts in the first place.
- Each `lua_State` preloads: a whitelisted standard library (`base/string/table/math/bit32`) + the `apollo.*` modules + the error-handling framework (`os/io/debug` banned; `load` bans **unverified bytecode** — every byte string received at runtime is treated as source code; precompiled artifacts are the exception via §3.5's dedicated loading path: build-pipeline output + hash/version-header verification, never through `load`).

## 3. Module Loading and Hot Replacement

### 3.1 Module Shape

```
modules/lua/
├── src/                # shared Lua sources (packaged per version)
├── dev/                # dev hot-update directory (monitored in the dev profile only)
└── patch/<ver>/        # live patch directory (gradual rollout, delivered per-version)
```
- A module = a Lua source file + metadata declared in a header comment (`--- module: quest, version: 42, deps: attr, ship`). The loader (~200 lines on the C++ side) scans the directory, validates the dependency graph, and compiles into standalone chunks (`luaL_loadbuffer`, no joining into globals).
- **Module-private state goes into the module table (upvalue), never into `_G`** — hot replacement swaps only the module-table reference; other system parts obtain it through "module handles" (registry refs); stale references from a module's old code are reclaimed in a GC cycle after the swap (reference counting is infeasible; liveness is decided by version).

### 3.2 Hot-Replacement Protocol (atomicity and rollback)

```
Control plane (GM panel/ops tool) → admin message → main thread:
  Phase A (worker threads, logic not interrupted)
    1. Read the patch directory → verify hash → compile the changed modules (deps in topological order)
    2. Smoke: run the "self-check case set" in the new state (every module must carry smoke tests, same source as CI)
  Phase B (main thread, tick boundary, O(1))
    3. Replace the table references of all involved modules at once (old tables go to the "freeze zone")
    4. Broadcast `ModuleReloaded{module, version}` (the script-side onReload hook re-registers, e.g. re-hanging event subscriptions)
  Phase C (observation window)
    5. Canary trial-run in scenes for N ticks (instruction budget/error-count monitoring)
    6. Over threshold → the main thread swaps back the old-table snapshot (freeze zone → active zone), broadcast a reload pseudo-event
```

- At most one replacement per module per frame; entity messages arriving during the replacement follow "old logic finishes the current frame" — determinism first, no fine-grained transactions (players perceive a one-frame delay).
- Attribute/entity data lives on the C++ side, and **hot replacement carries no player state whatsoever** — a direct dividend of the "data stays out of scripts" decision.
- **Rollback must persist the current-version pointer (added 2026-09-29)**: an in-memory table swap is valid only while the process lives — a crash before rollback makes the restart reload an already-condemned version (a bad-version crash loop). The rollback action also writes back the persistent current pointer (the patch directory's version manifest); restarts load "the latest known healthy version" by default.
- **Coroutine upgrade semantics**: old coroutines still suspended at the table swap **keep executing to completion or timeout on the old table in the freeze zone** (async coroutines already have a timeout upper bound, §8); all new coroutines use the new table — no "rewriting running coroutines mid-hot-update" (equivalent to breakpoint-style freezing, same verdict as §7.4); old function references held by old coroutines die naturally on completion (same path as §3.1's module-table GC reclamation).
- **Canary granularity = per scene thread**: one state per thread (§2) lets the table swap run independently per scene thread — the admin command is posted into each target scene thread's task queue, each swapping at its next tick boundary (same pattern as §7.1 attach); the canary is "some scenes swap first + health-score observation + full rollout", with the global version matrix queryable in §7.2's state surface. (Phase B's "main thread" reads as "the target scene thread" under multiple scene threads.)
- **Zero-migration discipline for module-private state**: hot updates **do not migrate** old-module upvalue state and provide no `onUpgrade(old_state)`-style migration function — state that must survive across versions belongs in C++ authoritative data or the DB (a corollary of §1's "data stays out of scripts"); module upvalues hold only rebuildable caches/counters. Providing migration facilities = encouraging moving authoritative data into scripts; this red line stays closed.
- **Implementation-status note (2026-10-15)**: Phases A/B have landed — `ScriptRuntime::prepare_module(spec, source)` runs the full table-swap protocol (compile → evaluate → smoke → load the prepared image) inside a **standalone preparation sandbox** (a second ScriptRuntime instance, lazily created), returning `PreparedModule{name, version, deps, bytecode, bytecode_hash, error}` (the artifact = `lua_dump` strip=0 own bytecode + fnv1a64 hash, consistent with §3.5's `lua_precompile`; **xmove is impossible across independent lua_States, hence the handoff goes through in-process bytecode**, never through the sandbox's `load`); `commit_module(prepared)` executes at the owning thread's tick boundary: hash-integrity check (reject empty/swapped artifacts + book a fault) → load (`"b"`, Lua self-verifies the artifact header signature) → evaluate → table check → `finish_module_swap_` (atomic table swap + freeze zone + circuit-breaker reset + onReload, sharing the tail with `swap_module`). **Smoke does not re-run** (the preparation face already verified it — re-running the self-check would move the cost Phase A saved back into Phase B, and add a second-execution difference surface). **Contract**: the control plane calls prepare/commit serially; the prepared image accumulates in topological order — dependency modules must first be prepared in place (modules swapped across preparation faces are not in the image; error `missing dependency on preparer`); the owning face's commit likewise checks dependencies in place first. The choice of Phase A's host thread belongs to the control plane (`apollo_script` has zero apollo dependencies, no thread pool introduced). **The current-version-pointer persistence has landed** (against the bad-version crash loop): `ScriptConfig.version_store_path` (the patch directory's version manifest; empty = off) — on a successful table swap (`finish_module_swap_`) or successful rollback (`rollback_module`), the whole table is read-modified-written and atomically renamed back as `<name>\t<version:016x>` (when Windows CRT rename won't replace an existing target, fall back to delete-first-then-rename — the tmp is fully written before deleting, so no half file ever appears at the target location); `current_version_manifest()` lets the control plane read "the latest known healthy version" on restart. There are exactly two write moments (successful swap/commit, successful rollback) — prepare never writes (the version is not yet activated), and the preparation sandbox builds a separate config with a cleared path to avoid accidental writes. The manifest is the same family format as §3.5's cache manifest but with the opposite access face (written at runtime, read by the control plane), in a separate file `module_version_store`. **The patch-directory read and hash verification have landed on the control plane** (step 1 of Phase A's engineering face, "read the patch directory → verify hash"): `load_patch_directory(dir)` (`patch_loader`, manifest-driven per-entry) — the source hash must pass (mismatch = tampering/corruption; that module is refused loading into errors, not thrown); bytecode hash / format_sig mismatch = drop the bytecode, keep the source (the artifact falls back and remains usable, same discipline as §3.5's version header); a missing/all-bad-lines manifest = a whole-directory error. This face only does "read + verify + carry the artifacts out" — compiling/smoking/table-swapping belong to `prepare_module`, and the deps topological order belongs to control-plane orchestration (Phase A step 1's "including deps topological order" is composed from these). **The Phase C canary observation-window verdict primitives have landed**: `ModuleCanary` (`module_canary`, observation window + over-threshold early failure) — after submission, `begin()` takes the runtime tick as the window start, the control plane `tick()`s the owning thread beat by beat (same window discipline as §7.1); within the window, fault attribution goes through the per-module fault ledger fed by the `call_module` path (`module_faults_since` is independent of the circuit-breaker's sliding window — the canary window N is a control-plane parameter, the breaker window W is a breaker parameter, not cleared with the breaker's reset); over-threshold early condemnation (without waiting for the window to fill); promote (full rollout) and rollback are driven by the control plane over the existing `commit_module`/`rollback_module` per the verdict — this primitive holds no second table-swap path. **The per-scene-thread canary delivery orchestration has landed** (Phase A engineering face, "multi-runtime delivery wiring"): `ModuleRollout` (`module_rollout`) — one preparation serves all targets (the orchestrator holds its own preparation sandbox, prepares the whole set in Kahn topological order, a dependency cycle errors `cyclic dependency in module set`; the same `PreparedModule` is handed to N `commit_module`s, same Phase A in-process bytecode-handoff discipline), and verdict advancement is a pure state machine (never touches Lua); table swaps/rollbacks go only through the existing `ScriptRuntime` face. The delivery shape is a **per-target stepped queue** (`pending_canary`/`pending_promote`/`pending_rollback`) rather than a synchronous traversal — Phase B's commit must execute at the target owning thread's tick boundary (§3.2 canary granularity + §2 one state per thread) and cannot be called synchronously across threads by one loop; the control plane posts each step into the corresponding target scene thread's task queue per the queue (§7.1 attach-style posting), and a single-gameThread host can drive it directly in sequence (the equivalent synchronous form). The phase machine kCanaryPending → kObserving → kPromoting / kRollingBack → kPromoted / kRolledBack (in-flight/parameter/dependency-cycle/empty-artifact failure → kFailed with zero targets touched); calls in an illegal phase or with a role mismatch silently no-op (per-frame unified driving by the host is legitimate use). The observation window takes "all canary-face submissions complete" as T0 (each target's window start = that runtime's current tick); one canary per (canary target, module); **any window condemned = early failure turns into rollback** (without waiting for the remaining windows to fill), all windows full and healthy = verdict good, promote. A good verdict is never rewritten by a promote failure — promote failure is a per-target error (the target stays on the pre-patch version; the retry face goes to the host); **canary-face load failure = condemned, turn to rollback** (same-family discipline as the smoke/load gates). Rollback goes in reverse topological order (withdraw dependents first) and writes back the current pointer (existing-face semantics). The same orchestrator instance can run multiple rounds serially (prepare is only allowed again from a terminal state; the preparation sandbox persists with the instance so already-prepared dependencies stay visible across rounds; the handoff face `prepared_` is cleared per round). `apollo_script` still has zero apollo dependencies (the target face takes only `{key, ScriptRuntime*}`, no Scene introduced); the **transport face** of per-scene-thread admin commands (admin/control-channel forwarding to the target process) still belongs to host-side wiring.

### 3.3 Coordination with Configuration Hot Updates

- L1 static configuration (attribute-sync.md §2.1) is delivered in per-version directories; old and new versions coexist (scenes with old clients keep using the old configuration), and the **configuration version is sent to the client along with the entity snapshot** (`attr_schema_version`, see attribute-sync.md §7.2) — preventing semantic drift between old and new entities after a configuration hot update.
- When a configuration change needs script cooperation (a numeric revision forcing a formula rewrite), the same patch carries both: configuration first, then scripts; the script version is enabled only when it is higher than the configuration version (version partial-order check).

### 3.4 Contract-Table Loading (contract.lua, sdk-contract §10.6 v3, added 2026-09-29)

- `contract.lua` is the Lua table apollo_gen emits in the same batch from the contract source (attr table/message routes/write whitelist — the server-side dual form of the same content as semantic.json): `require` and use, no compilation step (optional luac precompilation ships with the Lua distribution). Loading and hot updates go through the same table-swap protocol as §3.2: new table compiled → smoke (route-integrity check: if bin has a message with no Lua handler, refuse the swap — the scripting-side execution point of sdk-contract §10.6's load-time consistency gate) → atomic swap at a tick boundary.
- **Loading-face shape** (guaranteed by the same apollo_gen batch, golden checked in; same shape as the loader's consumption face, preventing the generator from emitting a table the loader can't load): a flat `routes` table (reflect entry id → handler name, one-to-one with the reflect entries of `M.msgs`, handler convention = message name) + the `write_whitelist` integer attr-id array (`predict=client_predicted`; names reverse-looked-up via `M.attrs`) + `version`. Metadata tables like `M.msgs`/`M.attrs` are kept for introspection; the loader consumes only the three items above.
- **Message-handler binding**: uplink business messages are dispatched to Lua by the C++ frame router per `contract_route` (id → handler name) — handlers register inside module tables, module header comments declare `handles: msg_a, msg_b`, the loader validates this against the contract route table, and a miss is a startup red.
- **Datafying the write whitelist**: §4/§5's `ScriptWriteWhitelist` bitmap is built from contract.lua (the whitelist is still generated from the contract's `predict` bit — the sdk-contract §5 mechanism unchanged; the carrier changes from generated constants to contract-table data); on a hot contract-table swap, the whitelist swaps at the same tick boundary.
- Version partial order follows the same rule as §3.3: a contract-table version is enabled only when ≥ the version of the script patch consuming it — adding a contract field and the handler patch using that field must be in the same batch, or table first, then patch.
- **Host startup loading has landed (added 2026-10-15)**: cell `--script-handlers <file>` / `--script-contract <file>` — the startup load order is handlers face → contract → boot sources (first beat of the gameThread, §2 single writer; the contract-loading gate resolves each route's `resolve_handler`, and a handler not already in place refuses to load; boot sources may read the `contract` global). A failure at any step only warns without stopping (same discipline as boot sources; faults go through the runtime event face). The contract-route handler placeholder module ships with the repo (`apps/room-server/scripts/contract_handlers.lua`, 45 no-op placeholder routes — the loading gate checks existence only; the gameplay batch fills in entities per message semantics; when apollo_gen adds a reflect message, the row must be added in sync, with `contract_handler_tests` gating the full load path in lockstep via the golden contract + the in-repo handler module). The `call_route` wiring that dispatches uplink business messages through the C++ frame router to Lua handlers still goes with the gameplay batch.

### 3.5 Bytecode Cache and Patch Shape

- **The cost account**: every startup and every hot-update Phase A must `luaL_loadbuffer` the full module set — at a hundred-odd modules of a few KB each, compiling the whole package is a perceivable startup cost (on the restart path it happens serially on the loading thread). The cache moves compilation from runtime to build time.
- **Shape**: **the patch directory carries precompiled chunks directly** — the build pipeline produces `<name>.luac` per module (luac -o or the host's `string.dump`), and the manifest records the triple `(source hash, bytecode hash, Lua version header)`; loading verifies per the manifest: source hash against tampering, **version-header mismatch refuses to load and falls back to source compilation** (the bytecode format is bound to the Lua minor version — the execution point of §2's version-lock discipline). The dev directory still uses sources (load-on-save; a cache has no benefit).
- **Only three invalidation rules**: Lua version changes / source changes / loader-logic changes — everything else is a hit; no disk management beyond the version manifest.
- **The red line unchanged**: `load` bans bytecode for **runtime strings** (§2); cached artifacts go through the dedicated loading path (the bytecode branch of `luaL_loadbuffer` + manifest verification), never through `load` — the "bytecode ban" bans untrusted sources, not our own build artifacts.
- §3.4's contract.lua is precompiled in the same batch (changes are rare but it loads at every startup).

## 4. C++ Service Exposure: Interface Shape and Cost

### 4.1 Startup Injection (the only channel)

```
Server::start() (Bootstrap phase, see architecture-review.md §6 phase 4)
  1. Container (core::di) assembled —— all service objects exist
  2. Binding registry: explicitly lists the exposed surface (whitelist-based, not auto-reflecting all services)
     apollo.attr   → AttrServiceAPI (≤10 bound functions: get/set/emit/dirty/onChange/...)
     apollo.scene  → SceneAPI (spawn/move/broadcast...)
     apollo.db     → DbAPI (query/execute + coroutine-style callbacks, base in §8)
     apollo.net    → SessionAPI (send_event/subscribe)
  3. Each module table is hung on the lua_State root registry; startup self-check: call a smoke function once to verify handles
```

- **Binding is validation**: at runtime there is no "find a service by string" path on the Lua side (no `apollo.services.find("db")`); whatever function is missing from a module table surfaces once at the startup self-check, not as a runtime nil error.
- What is taken out is a **stable pointer handle** (lightuserdata or a custom metatable), not a fresh allocation per call; bound function signatures stay thin (table params/return tables), zero copy across the boundary (only pointers + shared byte buffers move).

### 4.2 Prohibitions (explicitly listed as code-review red lines)

1. Binding `ApplicationContext` (the old string container) or any "look up a service by name" API into Lua is forbidden (architecture-review.md P0-1).
2. Scripts directly calling the attribute store's write interface to bypass the whitelist is forbidden (§5's hook entry is the only write path) — otherwise authority, validation, and audit all fail at once.
3. Scripts holding raw C++ entity pointers across ticks is forbidden (the entity may be freed) — the Lua-side entity handle = weak reference + validity query `entity:alive()`; stale access returns an error, not UB.
4. Modifying attributes in any tick phase other than phase 3 (after simulate) is forbidden (see §5 hook timing) — preserving the temporal trimmability of the single-writer discipline.

## 5. Attribute Hooks: the Integration Shape of onAttrChanged

### 5.1 Timing (aligned with attribute-sync.md §10)

```
simulate phase (C++/Lua business mutates attributes, marks dirty)
recalc phase (derived-attribute recalc, pure C++ dependency graph; the formula-from-Lua exception is in §5.3)
  └─ script hook window: after the dirty set is fixed, before broadcast collection
     for each (entity, attr) in dirty:
        if attr in ScriptWriteWhitelist:
            new = lua:onAttrChanged(entity, attr, old, new)   // only a modified value or unchanged may be returned
            (script modification of non-whitelist attributes is rejected —— return value discarded + counted warning)
collect phase (delta/snapshot assembly of §3.2)
```

- The `old/new` the hook receives are C++-side snapshot copies (two int64s/one string reference), **lock-free**: both belong to the owning thread.
- **Reentrancy guard**: a call to `apollo.attr.set()` inside the hook counts as a second-order change — it lands in the **next tick's** dirty set (the current tick's set is already fixed); modifying the same attribute inside the hook is forbidden (infinite-loop protection: at most N script adjustments per (entity,attr) per frame).
- Listener registration: the C++-side hook table stores callbacks as Lua refs (`apollo.attr.register_listener(entity_scope, handler)`); on hot replacement the old callbacks lapse together with the old table (new modules re-hang via `onReload` — §3.2 event hook).

### 5.2 Cost Control

- Zero calls at idle by default: when `ScriptWriteWhitelist` is an empty bitmap, the entire hook window is skipped (emptiness check on one 64-bit bitmap, O(1)).
- Instruction budget: the entire hook window totals ≤ X instructions per frame (default e.g. 200k, on the order of 0.5ms, calibrated by measurement); over budget → remaining hooks this frame skipped + counted warning, recovering next frame.
- Replacement for subscription-style fan-out: systems wanting "attribute changes drive AI" should not hand-roll one listener each — make a **raised abstraction** at the scripting layer (`apollo.ai.watch(entity, attrs, handler)` merges listens in batches at the framework layer, avoiding N entities × M listeners full scans).

### 5.3 Formulas as a Special Case of Hooks

- L4 derived-attribute formula functions hang on a "pre-recalc" variant of the same callback mechanism: `calc_attr(entity, id) -> value`. The dependency graph stays in C++ (topological scheduling, cycle checks, recalc sets); the formula bodies live in Lua.
- Formula hot replacement = one module hot replacement (the module holding the formula functions); with dependencies unchanged, the recalc set changes zero (entities already verified against the old formula are lazily recomputed — by default the new formula simply applies from the next moment; no migration action).
- Performance: for high-recalc-frequency attributes (e.g. HP regen), formulas stay in C++ (outside the whitelist, off-limits to scripts); only what needs scripting goes to Lua — **all C++ by default; scripting is an explicit choice**. This is §1's criterion landing on formulas.

## 6. Sandbox and Performance Budget

| Dimension | Mechanism | Behavior once triggered |
|---|---|---|
| Instruction count | Per-state per-frame budget (lua_sethook COUNT in a fine-grained two-stage form: coarse check every 10k instructions, precise check on overrun) | abort the current script call → log the error → the entity falls back to default behavior (e.g. stand still) |
| Memory | Per-state cap + `lua_gc` step limit (incremental GC; no full GC frame stalls allowed) | over limit → refuse new allocation requests → the module is marked unhealthy and goes under observation |
| Errors | C++-side try-catch-lua errors (`lua_pcall` classified: syntax/runtime/memory) | runtime error → log + count + behavior fallback; **the process does not crash**, no player drop |
| Infinite loops | naturally covered by the instruction budget (unlike timeout-signal schemes, no multi-threaded watchdog needed) | same path as the instruction overrun |
| Cross-state isolation | one scene, one thread, one state; scene migration = state migration (kill one, start one; player data in C++ unaffected) | — |

- Debug face: the error audit channel (error summaries carrying module name+version+data snapshot) goes into `docs/design/attribute-sync.md`'s BI bypass, independent of the game channel, letting ops query "module X's error rate spiked after the hot-update upgrade".
- Canary linkage: the module health score (error count/budget-overrun rate) drives §3.2's rollback threshold.

### 6.1 Fault Notification Contract: Three Event Levels, the Cold-Path Single Point, and Module Circuit Breaking

§6's table entry "log the error → entity fallback" defines only the **in-engine** handling; the external notification contract of "engine → ops/business" (what the event looks like, who consumes it, whether the scripting layer has programmable hooks) had zero design until now — this section finalizes it. Position first:

**The engine provides no script-implemented fault SPI (review red line)**, for three reasons: (1) at fault time the scripting layer is the least trustworthy component in the room — a watchdog's callback must not depend on the watched (letting the module that blew the budget execute onFault is letting the disease write its own case report); (2) hot-path callbacks break the tick budget and determinism (fault handling must be O(1); what runs inside the callback body cannot be constrained); (3) the script self-handling channel already exists — a handler capturing its own errors with pcall is business logic (self-captured means no fault is triggered; the semantics are already right), and the engine contract does not overlap with it. §19.5.1's candidate direction, "cold-path single point", is on this basis **landed as a read-only exit**, not a script-implementable SPI.

- **Three event levels** (same exit; the level decides the action):

| Level | Trigger | In-engine action | External |
|---|---|---|---|
| WARN | a single call consumes ≥ 80% of budget without exceeding it | none (execution completes) | one event (debounced: at most one per (module,handler) per 256 ticks) |
| FAULT | over budget / runtime error / sandbox violation | abort + entity fallback (§6 table, existing semantics) | one event + counter +1 |
| TRIP | circuit-breaker trip/release (see below) | module-level quarantine | one event (low-frequency, discrete) |

- **ScriptFaultEvent fields (structured, into the ERROR bypass log line)**: `ts_wall_ms + tick` dual-write (clock-and-time §7 discipline), `scene` (scene-thread identity), `entity_id` (when entity context exists), `module + version` (§3.1 header-comment metadata — "which module at which version" directly answerable), `handler`, `kind` (budget_exceeded / runtime_error / sandbox_violation / circuit_tripped / circuit_recovered), `consumed/budget` (instruction counts, a byproduct of §7.3's dual-role hook), `action` (warned / aborted_rolled_back / quarantined). The field set is **closed** — downstream (collector/exporter/webhook) routes by field, never parsing free text.
- **Exit = the cold-path single point `onScriptFault(const ScriptFaultEvent&)`**: one fixed C++-side function slot per `lua_State` (i.e. per scene thread, §2), non-virtual, no registry, not replaceable by scripts; the default implementation does three things, all O(1): one ERROR bypass log line (logging §3.1 — never into the shared queue), a MetricRegistry counter increment (`script_fault_total{module,kind}` / `script_budget_warn_total{module}`), and advancing the circuit-breaker state machine (next item). **Explicitly forbidden** on the fault path: synchronous IO/HTTP/cross-process calls — the external dispatch right belongs to the collector/exporter side (logging §5.2, the same exit as webhooks); the engine only produces events and counters.
- **Circuit breaker (module-level, against "the same bad module burning through every tick")**: the M=3rd FAULT of the same module within sliding window W=1000 ticks → mark `quarantined` for Q=600 ticks — during quarantine, that module's handler calls short-circuit directly (entity falls back to default behavior, never entering Lua); release goes **half-open**: at quarantine expiry one call is let through, and another FAULT doubles Q (capped at one long cooldown; the concrete ceiling calibrated with the capacity batch); **hot updates auto-reset** (§3.2: a new table means a new version with a clean ledger — a fixed module need not wait out the cooldown, a direct dividend of "hot update as the repair channel"). Breaker state goes into §7.2's state surface (quarantine list/remaining ticks/history); W/M/Q are startup-time configuration, not hard-coded.
- **Idempotence and aggregation (the guarantee against flooding the outside)**: the engine-side debounce applies only at the WARN level (table above); the FAULT level aggregates naturally via **counter semantics** — what downstream sees is the rate of `script_fault_total`, not event-per-event; TRIP is inherently low-frequency. Alert thresholds/silence windows/rate limits are exporter-side rules (logging §5.2), not in the engine — configuring another alert-rule set engine-side = two sources of truth.
- **Determinism and replay**: a fault's **handling** (abort/fallback/breaker quarantine) is a deterministic state transition inside the world thread's tick, automatically reproduced by recomputation replay; the fault **event itself** never enters the recorded input stream (engine-produced observation data, not world input) — battle-determinism §5's input sequence excludes it, and replay correctness does not depend on "whether the alarm happened".

## 7. Online Debugging and Performance Attribution: attach Execution / Lua State Introspection / profile

> The semantic layer defers to `docs/architecture/observability-watcher-and-runtime-introspection-design.md` (architecture/ generation) — the Watcher Tree, Passive Query vs Controlled Action grading, AccessController; this section covers the scripting domain's three items (attach execution, the Lua state surface, performance attribution) and one position (no breakpoint debugger). Channel and ownership follow G-5's two-part placement (net-abstraction §7 P3, architecture-review §16.8.3-⑤): detection primitives embed in the ScriptHost (in-module), interactive tools belong to the apps/ admin face.

### 7.1 attach Execution: Single Admin Entry + Tick-Boundary Sandboxed eval

- **Precedents**: KBE ships a telnet service per process, password-gated with a configurable execution layer (roomserver.cpp:292-293 `pTelnetServer_->start(telnet_passwd, telnet_deflayer, …)`); after command decoding it enters the Python interpreter for **online execution** (telnet_handler.cpp:801-812, eval after `PyUnicode_DecodeUTF8(command)`); skynet's debug_console is a console service that `call`s any service to execute Lua online (architecture-review §16.2, debug_console.lua:147-174).
- **apollo's trade-off**: do not copy "one listening port per process" — converge to a **single admin entry** (authentication/audit/permission grading done once) + control-channel forwarding to the target process/target scene thread (skynet shape); in the single-process phase the admin entry is local. Off by default after authentication, bound to the intranet only (KBE passwd precedent).
- **Execution semantics (single-writer discipline)**: debug commands are posted into the owning scene thread's task queue, executed at a **fixed debug point in the next tick**, results returned — no thread ever touches a `lua_State` directly (a corollary of §2's one-thread-one-state; skynet's call is isomorphic: the console posts a message, the target service executes in its own context).
- **The eval environment = a standalone debug env**: a restricted superset of §6's sandbox whitelist — read-only query APIs + a few controlled actions (GC stepping, module-health reset); no business-write permission (no `apollo.db` write path); result-size caps + rate limits (against fat-fingering flooding the control channel); the instruction budget governs eval too (interrupt-on-timeout with a report — tick determinism over debugging convenience).
- **Permission grading** (observability-document scope): state queries = Passive Query (available by default after authentication); eval execution / GC and similar actions = Controlled Action (higher authorization + audit log — who ran what when, the same-style bypass as §6's error-audit channel).

### 7.2 The Lua State Surface (what to query — four inventories)

| Panel | Contents | Source/mechanism |
|---|---|---|
| Memory and GC | per-state memory (`collectgarbage("count")`), GC step/pause parameters, cap watermark and over-limit events | the read exit of §6's memory dimension |
| Coroutine inventory | each coroutine's state (running/suspended/normal/dead), suspend counts, awaited wake conditions, overdue coroutines (leak detection) | the coroutine-style async base (§8 async model; the §4.1 `apollo.db` / §9 net intersection) |
| Modules and versions | loaded chunks/module tables + each module's currently running version, the history of hot replacements | §3.2 hot-replacement audit — "which version each live module runs" answered in one query; version drift = hot-update incident localization |
| env sampling | read-only snapshot of a named module's env top level (depth/byte limits) | controlled inspection of §3.1 module-private state |

- The semantic layer hangs off the observability document's `/script` path branch: the first three classes = Value/Collection nodes (Passive Query), eval = Action nodes (AccessController-governed); trend classes (error rate/budget-overrun rate time series) go to MetricRegistry — the "metrics=trends, watcher=current state" scope per that document.
- **Same-pattern precedent (KBE watcher)**: each subsystem's own `initializeWatcher()` hangs its values into the path tree (serverapp.cpp:165-177: Network/Resmgr/threadPool/WatchPool each hang their own), queried remotely over a network channel via `queryWatcher` (:181-198); the GUI consumer is the external tool guiconsole/WatcherWindow — "detection primitives in-process, aggregated presentation in external tools" is isomorphic to G-5's two-part placement.

### 7.3 Performance Attribution (profile): the Dual-Role Instruction Hook + External Sampling on the C++ Side

- **Lua side: one hook, two roles**. §6's `lua_sethook` COUNT hook is already mandatory on the hot path (budget enforcement) — attribution statistics are its second role: per-module/per-handler instruction counts and wall-time buckets, aggregated at tick end into §7.2's state surface and MetricRegistry. "Which module's hooks ate §5.2's budget" and "which formula is hottest (§5.3)" become directly answerable. The increment = counter bucketing, no new hot-path mechanism (the hook cost is already paid).
- **C++ side: no self-built profiler**. Sampling external tools (perf/Tracy class) are naturally compatible with the single-writer thread model — thread names are the scene attribution; module obligations are only two: frame-phase markers (frame markers, aligned with attribute-sync §10's six-phase sampling intervals) + unstripped symbols. Precedents: BW bw_profile / KBE guiconsole are both external tool processes (architecture-review §16.8.2 table — "aggregated presentation in external tools", same shape in both families).
- **Infinite-loop detection = existing design** (§6: naturally covered by the instruction budget, unlike timeout-signal schemes, no multi-threaded watchdog needed) — this section adds one thing only: overrun events upgrade from "log + entity fallback" to also entering the state-surface alarm (which module/which handler triggered it, that frame's instruction count).

### 7.4 Debug Capability Boundary (explicitly not done, against future re-litigation)

- **No breakpoint-style debugger**: a breakpoint suspend = **whole-scene freeze** of the single-writer thread (every entity's tick on that thread stalls) + tick-determinism destruction (the inverse of G-7's argument) — an MMO logic server's debugging shape is the trio "online eval + state introspection + offline audit (§6)", not "stop the world and set a breakpoint". KBE telnet / skynet debug_console likewise have only eval and queries, no breakpoint debugger.
- The other half of preventive debugging is already in §3.2: the pre-hot-replacement worker-thread smoke (smoke case set + canary scene trial-run + health-score rollback) — a new version proves itself in a shadow environment first.
- Phasing: this whole section follows G-5 in the same batch (net-abstraction §7 P3 two-part placement) — detection primitives land with the owning module, the admin interaction face belongs to apps/; interim dev-period means = logs + §6 error audit + §3.2 version audit.

### 7.5 GM/Operations Command Surface

§7.1-§7.4 are framework-side debugging; gameplay GM (grant items/ban/kick/modify attributes) had zero design until now ("GM" appeared in the design docs only as a source of admin messages) — this section adds three things: the command table/permission grading/audit storage. **Zero new pipes**: GM commands travel the same road as attach (single admin entry → control channel → target scene thread execution at the **tick boundary**, §7.1).
- **The command table = registry-driven, not eval**: a GM command is a named function declared inside a Lua module (module header comment `gm_commands: give_item, kick, ban …` — same pattern as §3.4's `handles:` declaration), parameters carry a schema (count/type/range), validated by the C++ side before dispatch; **the GM surface gets no arbitrary eval permission** (eval is §7.1's Controlled Action, high-risk and audited, not an operator's daily working surface). The command registry is validated at load time (duplicate names/unregistered handler = startup red), same family as §3.4's loading gate.
- **The write-permission relationship with the contract**: the GM-modifiable attribute surface = the contract.lua's independent whitelist **`gm_write`** (listed separately from the script `predict` whitelist — GM-surface ⊇ script-surface is a configuration fact, not a mechanism overlap); GM writes go through `apollo.attr.set` on the same hook/audit road (§5) — **no direct-write channel bypassing the attribute pipeline is provided** (the authority/validation/audit trinity at the hook entry, the GM version of §4.2 red line 2). Read-only queries (player attributes/inventory) go through §7.1's debug-env read-only APIs, zero additions.
- **Permission grading connects to the observability AccessController**: GM commands declare a level (1 query / 2 operate / 3 high-risk — ban/rollback/coin-grant class), operator-role → level mappings go into configuration; level 3 defaults to **two-person review** (initiating + authorizing accounts; BW/KBE lack this layer — an apollo strengthening, deployable downgraded to single-person + high-frequency audit alarms). The framework-side Passive/Controlled grading (observability document) is unchanged; GM level is business granularity on top of it.
- **Audit storage**: every GM command lands in a **standalone `gm_audit` audit table** — (operator account, wall_ms + tick dual-write (clock-and-time §7), target entity/account, command name, parameter snapshot, result code); domain-separated from the journal (journal = the world-state change stream, gm_audit = the operations-behavior stream); the query face hangs off observability's `/gm` branch (who did what to whom when, answered in one query); **rejected commands are also audited** (a rejection is an event too).
- **Determinism and replay**: GM commands going up through an admin session = one class of the ordinary intent stream — battle-determinism §5 input recording (session=admin) naturally includes GM input, and recomputation replay automatically includes GM intervention; GM world-changes and player operations have equal standing in the decision domain (tick-boundary inputs), determinism unbroken.
- **Where kick/ban execute**: session disconnect = the net layer's close (net-abstraction §2 four actions); a ban = a risk-control record consumed by the login-app admission gate (violation_score family, net-abstraction §4.3) — the GM command is the trigger; the mechanisms belong to their own domains and are not rebuilt in the scripting layer.

## 8. Async Task Model: Redis/DB/Cross-Server under Single-Writer Threads

> Once business logic converges onto scene-thread single writers (§2 / attribute-sync §10), "one Redis read / DB query / cross-server call" can no longer block in place waiting — waiting stalls the whole scene's tick. This section fixes the architecture-level async wrapper: **C++-side callbacks + request_id handoff, Lua-side coroutines**, each layer taking its best-fit model. (The "§async model" originally cited by the §9 intersection table is this section; that dangling reference closes here.)
>
> **Implementation status (2026-10-04 reconciliation)**: this section is target-state design; the L0 execution layer is not implemented — P1-4 deleted the whole redis family (including the hiredis client); the Redis face waits for re-introduction with the cross-process batch; the DB face is currently file archives + `PersistJournal` (no SQL execution layer); cross-server RequestReply is unwired. The "hiredis async interface / DB Command queue" rows of the §8.2 table read per this scope.
>
> **Implementation status (added 2026-10-15: the L1 handoff layer + L2 script layer have landed)**: `ScriptRuntime` delivers §8.2's L1 handoff primitives and the L2 coroutine face — `register_async_service(name, handler, timeout_ms)` is the extension point for the L0 execution layer (the host later plugs in the real Redis/DB/cross-server backends per batch; acceptance returns immediately without blocking the owning thread); `apollo.async.call(svc, ...)` internally yields and suspends (unknown service / main-thread call = fast-fail error); the completion faces `complete_async`/`fail_async` enqueue from any thread, and `drain_async()` delivers uniformly at the tick boundary (the handoff is a message, not a future; even same-thread never inlines); `cancel_pending(reason)` is cooperative cancellation (terminated at the next drain with a cancellation error); `set_async_validator` is discipline 2's re-validate hook (invalidation terminates with an error, never injecting zombie results); all three disciplines landed — resume only at drain boundaries, injected errors (timeout/cancel/invalidation) still fire the fault but don't count toward the module breaker (the ops final state belongs to the host), and per-service configurable timeout upper bound + `async_default_timeout_ms` global default. The coroutine registry + `coroutine_snapshot()` is §7.2's coroutine inventory (handle/state/suspend reason/awaited request/timeout/birth tick/overdue leaked); script-created `coroutine.create/wrap/resume` are synchronously swapped into the registry (no blind spots in the inventory; the instruction hook and budget govern across yields). §8.2's `apollo.async.all` concurrency combinator and the L0 real backends still await their own batches.

### 8.1 Three-Model Comparison (why this choice)

| Model | Pros | Cons (game-server context) | Verdict |
|---|---|---|---|
| Callbacks | zero dependencies; explicit control flow; engine-dispatch friendly (completions delivered uniformly at tick boundaries) | callback hell, scattered error handling; **lifecycle traps**: the entity/session may already be destroyed before the callback fires (every callback needs a validity check) | **adopted on the C++ side** (the handoff primitive, §8.2) |
| Future/Promise | value-semantic container, composable (when_all/then); JS Promise chains + async/await look nice | C++ `std::future` has no then, and `get()` **blocks** — a get inside a tick stalls the frame (red line); futures with then (folly/asio) need an executor framework brought in, benefit out of proportion to complexity; JS Promise is essentially = microtask scheduling + a state machine, and its "drain the microtask queue every turn" and "resume at tick boundaries" are two implementations of isomorphic semantics — Lua coroutines + a fixed debug point are already the simpler form | **not introduced** (no future framework; the JS-style look is obtained natively in Lua coroutines) |
| Coroutines | sequential code writing async (script/designer friendly); **suspension costs zero threads** — tens of thousands of suspended coroutines on one thread occupy no OS thread, a match made in heaven with the single-writer model; suspension points explicit (yield is "waiting on IO"; timeouts/auditing can hang on the suspension point) | cross-yield invariants: world state changed while suspended (entity died/went offline/scene migrated) → **must re-validate after resume**; cooperative, not preemptive → the timeout upper bound must be explicit | **adopted on the Lua side** (C++20 coroutines do not enter the engine side — the C++ side has few async points, all infrastructure; the complexity doesn't pay) |

**Precedent**: skynet is natively all-coroutine — `skynet.call` suspends the current coroutine awaiting the response message (lualib/skynet.lua:227 `coroutine_yield "SUSPEND"`, :18-26 the resume/yield primitive bindings, :415 wakeup dispatch); "message arrival → the corresponding coroutine resumes" is its entire scheduling paradigm; BW/KBE's script side, within what we have read, are callback-style lifecycle methods (the onTimer/onXxx families), no coroutine facilities. apollo takes skynet's coroutine look + its own tick discipline (resume only at boundary points).

### 8.2 Layered Wrapping (architecture levels)

```
L2 script layer (Lua coroutines)   local r = apollo.db.query(...)   -- yield suspends; the result is there on return
                                     apollo.async.all{a=..., b=...}    -- concurrency combinator: one yield awaits all (merged timeout)
L1 handoff layer (C++, scene thread) request_id → completion callback → scene-thread task queue (the same MPSC road as net uplink)
L0 execution layer (C++, IO/DB thread pools) hiredis async interface / DB Command queue / InterServerLink RequestReply
                                     —— neither blocking nor async IO ever happens on the scene thread
```

- **Execution layer**: the real IO of Redis/DB/cross-server runs on independent thread pools (modules/base/thread_pool) or async clients (hiredis event hook); connection pools and Command queues belong to modules/data (ssengine-reference §4.1's async DB Command model has its first consumer right here); cross-server RequestReply goes over InterServerLink (net-abstraction §5.7 — its §7 already ruled RequestReply control-plane-only; request_id is this layer's counterpart).
- **Handoff layer**: on completion → `(request_id, result/error)` is packed into the owning scene thread's task queue — **the handoff is a message, not a future** (a cross-thread future's shared state is lock/atomic synchronization; a message is one-way delivery — the same discipline as net-abstraction §3's "IO threads never hold game-data locks"). When the C++ business side genuinely needs async, it uses the same callback + request_id shape, never `std::future::get` (red line: any blocking wait inside a tick).
- **Script layer**: APIs like `apollo.db.query(...)` internally yield and register the request_id; once the completion callback enters the scene thread, resume happens at the **fixed debug point** (tick boundary, the same spot as §7.1 attach) and injects the result/error — synchronous semantics presented to the script. The coroutine registry (handle/suspend reason/timeout/owning entity) is the data source of §7.2's coroutine inventory.

### 8.3 Three Disciplines (game-server-specific constraints)

1. **Resume only at fixed tick-boundary points**: never touch a `lua_State` on an IO/DB thread (a corollary of §2's one-thread-one-state) — completion callbacks enqueue first; boundary points resume uniformly; determinism over latency.
2. **Re-validate after resume**: the world may have changed during the yield — before injecting the result, verify the entity's `alive()`, the session active, the scene unmigrated (the coroutine version of §4.2 red line 3); if invalid, the coroutine terminates with an error (the script side catches with pcall, going through §6's error audit), never injecting a zombie result.
3. **Timeout upper bound + cooperative cancellation**: every suspended coroutine carries a timeout (default configured per API class: DB seconds, cross-server hundreds of milliseconds); whichever comes first, timeout resumes with a timeout error (late results discarded + counted); on player logout/scene destruction, pending coroutines **run to the next suspension point and then terminate with a cancellation error** — a Lua coroutine cannot be safely hard-killed; only cooperative winding-down; overdue un-reclaimed ones are exactly §7.2's leak-detection targets.

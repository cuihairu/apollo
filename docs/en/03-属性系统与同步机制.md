# Entity Attributes and Synchronization

This page is an architectural reading guide to attributes, visibility, change tracking, and persistence. For Apollo's current implementation and protocol boundaries, use [Attribute system and synchronization](./design/attribute-sync.md), [SDK contracts](./design/sdk-contract.md), and the [game API](./api/game.md).

## Definitions and storage

Attribute definitions describe identifiers, types, defaults, visibility, synchronization policy, and persistence. Keep those definitions separate from each entity's mutable values. Shared metadata allows serializers, script bindings, validation, and client accessors to agree on the same contract.

An attribute container needs typed access, validation, and explicit change tracking. Derived attributes and modifiers require a defined evaluation order. Marking a value as changed does not by itself send it to a client or make it durable.

## Synchronization

| Mechanism | Responsibility |
|---|---|
| Initial snapshot | Establish the receiver's baseline |
| Dirty tracking | Record values changed since the relevant baseline |
| Delta batch | Send selected changes with sequence information |
| Visibility filtering | Restrict values to authorized observers |
| AOI events | Add or remove observers as entity visibility changes |
| Resynchronization | Recover after a missing or invalid baseline |

A client entering visibility needs a usable baseline before applying later deltas. A client leaving visibility must stop receiving data for that entity. Owner-only and public values require distinct visibility rules; AOI membership alone is not an authorization policy for every attribute.

Sequences and baseline references let receivers detect gaps. Batching and coalescing can reduce bandwidth, while bounded queues and explicit overload behavior prevent a slow connection from retaining unlimited change history.

## Broadcasting and persistence

Scene owns entity visibility and authoritative simulation changes. Network code consumes snapshots or queued output instead of mutating simulation containers from an IO thread. A computed viewer set is only one step in delivery: encoding, routing, socket output, and receiver application require their own integration.

Persistent player data is a separate responsibility from transient simulation state. Long-term changes and settlement must enter the persistence path, with explicit durable confirmation and business deduplication. A local attribute update or successful broadcast does not prove durable storage.

## Performance and validation

Measure storage layout, dirty-set size, observer fan-out, encoded bytes, and serialization cost before introducing pooling or specialized containers. Validate snapshot-plus-delta equivalence, visibility changes, duplicate and missing batches, slow clients, restart recovery, and durable settlement retries.

# 安全策略设计

> 目的：定义 Apollo MMO 的整体安全机制，覆盖客户端通信、服务间认证、GM/运营权限、数据保护，确保架构在对外提供 SDK 与运维接口时具备可控的安全保障。

## 1. 威胁模型概览
- **客户端攻击**：恶意客户端、协议篡改、重放、外挂、撞库。
- **网络攻击**：DDoS、MITM、端口扫描。
- **内部威胁**：越权访问、配置误操作。
- **数据风险**：敏感信息泄露、数据库被窃取、日志泄露。
- **供应链/插件**：恶意插件、依赖污染。

## 2. 客户端通信安全

### 2.1 连接加密
- 对所有 GateServer-Client 通信启用 TLS（可使用 OpenSSL/mbed TLS），或在应用层使用 AES-256-GCM/ChaCha20-Poly1305。
- 握手阶段采用 ECDH 派生对称密钥，支持证书更新。

### 2.2 消息安全
- 包头携带 HMAC（SHA-256），使用握手协商的密钥，防止篡改。
- 每个包包含 `session_id`, `seq`, `timestamp`，防止重放。
- 敏感字段（账号、支付等）加密或脱敏。

### 2.3 客户端验证
- 客户端登录需携带设备信息、版本校验、资源签名。
- SDK 采用白名单签名机制（验证 Game Package 的签名/哈希）。
- 接入 Anti-Cheat：行为检测、速度/AOI 异常检测、第三方反作弊 SDK（可选）。

## 3. 服务间安全

### 3.1 认证授权
- mTLS：内部 gRPC/TCP 连接使用双向 TLS，证书由内部 CA 管理。
- Token 策略：ServiceRegistry 分发服务 Token，内网调用附加到 metadata。
- ACL：在 Transport 层维护 allowlist/denylist，限制服务间访问。

### 3.2 配置与密钥管理
- 密钥/证书存储在安全配置中心（HashiCorp Vault/KMS），服务启动时动态获取。
- 禁止在代码库中硬编码密钥，配置文件需加密。

### 3.3 插件安全
- 插件包需签名验证（参见 `docs/15`），只加载来自官方发布的模块。
- 插件运行在受控沙箱内（限制权限、资源）。

## 4. 运维/GM 安全

### 4.1 鉴权
- 使用 OAuth2/OIDC（Keycloak/自研）管理运维、GM、运营人员账号。
- API Gateway 对所有运维 API 强制鉴权，使用 JWT + RBAC。

### 4.2 审计
- 所有操作记入审计日志：用户、操作、参数、结果、时间。
- 高风险操作（发放奖励、修改角色）需要审批/二次确认。

### 4.3 最小权限
- 区分运维、运营、开发、测试角色；不同角色访问不同服务与数据。
- SSH/数据库访问使用跳板机与命令白名单。

## 5. 数据与日志安全
- 数据库、Redis 使用专网或 VPC 内访问；对外接口最小化。
- 敏感数据（密码、SCN）加密存储；备份/归档数据加密。
- 日志脱敏：敏感字段（账号、手机号）在输出前脱敏。
- 对日志存储系统（ELK、ClickHouse）设置访问控制与审计。

## 6. 网络与基建
- 使用防火墙/安全组限制端口访问；Gate 前部署 Anti-DDoS/高防。
- 内部服务部署在 VPC/子网，利用安全组和 ACL 控制通信。
- 采用 WAF/IDS/IPS，对运营 API、管理端口做防护。

## 7. 故障与应急
- 定期进行渗透测试与安全扫描（依赖库、容器镜像）。
- 制定安全事件响应计划（CSIRT）：发现、隔离、修复、复盘。
- 为关键密钥与证书设定轮转周期和自动化更新流程。

## 8. Roadmap
1. 实施 TLS/mTLS、HMAC、Anti-Replay 机制，更新 NetCore/SDK。
2. 部署内部 CA/Vault，统一管理证书与密钥。
3. 引入 OAuth2/Keycloak 做 GM/运营权限管理。
4. 实现插件签名校验、RBAC/审计日志。
5. 定期渗透测试与自动化安全扫描（依赖、镜像）。
6. 建立安全事件响应流程与演练。

---

该策略文档指导安全相关实施，确保框架在上线和对外开放 SDK 时具备基本的防护能力。***

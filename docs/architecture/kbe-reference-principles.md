# KBE 参考原则

参考 KBEngine 的机制与工程边界，Apollo 的职责和命名以[当前架构决策](./adr.md)为准。外部引擎进程名保留其真实含义，不作为 Apollo 的候选进程清单。

## 运行时与生命周期

借鉴统一启动入口、公共服务运行时和明确的启停顺序。Apollo 复用现有宿主和模块装配能力，业务应用通过组合接入服务；避免让各入口分别实现依赖、生命周期与关停语义。

进程职责固定为 Login、Gateway 和 World。World 内的 PlayerStore 持有玩家资料与持久化；Login 内的 OnlineDirectory 持有在线目录、落点与迁移编排。共享应用服务不是新的业务进程。

## 实体、契约与脚本

借鉴实体元数据驱动属性、远程调用、脚本绑定和客户端代码的思路。Apollo 使用 XML/XSD 契约和生成器，服务端与客户端围绕同一契约生成产物。

线上契约、存储形式和脚本执行机制保持各自边界。契约声明或生成产物存在，不代表真实消息路径已经采用某种编码、版本协商已经完成，或数据库已经接入。

Lua 使用现有 ScriptRuntime 和 C API 绑定。脚本不能从网络或后台线程直接改写 Scene，也不能通过容器字符串查找绕过启动期服务注入。

## 模拟与可见性

借鉴空间运行时持有实体、AOI 和可见性状态的边界，Apollo 的对应对象是 Scene。Instance 关联 Scene，负责临时副本起止，复用既有八态生命周期。

跨服仍使用 World / Scene / Instance，保留玩家原区服归属并显式交接权威。跨服场景可以是持续场景，也可以关联临时 Instance；它不要求 Ghost、空间分片或无缝地图。详见[跨服场景设计](../design/cross-server-scenes.md)。

## 通信与权威

消息传输、受理、模拟执行和持久确认是不同结果，需要各自的关联与失败语义。可靠链路不提供业务恰好执行一次，迁移和结算仍需幂等键及权威代次。

同一玩家只允许一个可处理输入、推进模拟和提交权威写入的运行对象。迁移在途快照可以同时存在，待接管目标必须保持不活动；提交结果不明时先对账，禁止双端解冻。

## 运维与恢复

借鉴监督、结构化观测和受控管理入口，复用 machined、日志、指标和运行时内省原语。监督重启不等于恢复活动副本，目录重建不等于恢复玩家的唯一写权。

故障演练必须使用当前应用链路，验证档案、权威、路由和玩法结果；不能用旧进程拓扑的测试记录作为当前验收证据。

## 不采用的目标

Apollo 不提供另一种 Base/Cell 运行模式，不以无缝地图、Ghost 镜像和空间拓扑调度作为当前路线。也不为模仿外部引擎而增加同义对象、进程或命名。

机制是否采用取决于当前玩法、容量与故障恢复需求。未启用的跨服部署、外部存储和观测基建继续按照根目录任务清单中的触发条件实施。
